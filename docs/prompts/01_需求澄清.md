# 模板 01：需求澄清

> 用途：需求模糊或文档有歧义时，让 AI 先整理需求、列出歧义点向你确认，**不得直接动手实现**。

## 模板正文

```
【Context 背景】
项目：康伴 3D 数字人康养陪伴系统（FastAPI + PostgreSQL，CCRC 康养社区场景）。
当前阶段：Day{N}，已完成：{已交付能力摘要}。
需求来源：{PRD/TDD/口头描述 + 具体章节}。
相关现状：{涉及模块的当前实现状态}。

【Task 任务】
请基于上述材料整理本次需求：
1. 用你的话复述需求目标与验收口径；
2. 列出材料中的歧义点、冲突点和缺失信息（逐条编号）；
3. 对每个歧义点给出 2-3 个候选解释或方案选项。

【Constraints 约束】
- 只做澄清，不写任何实现代码，不创建/修改文件；
- 引用结论必须注明文档出处章节；
- 有不明白之处先提问，不得假设后直接推进。

【Expected Result 预期结果】
输出三节：《需求复述》《歧义与冲突清单（编号）》《待我决策的问题（含选项）》，
等我逐条答复后才允许进入实现。
```

## 本项目示例

```
【Context 背景】
项目：康伴 3D 数字人康养陪伴系统（FastAPI + PostgreSQL + pgvector）。
当前阶段：Day2 身份与权限模块，Day1 已交付 FastAPI 工厂、11 张基础表、0001/0002 迁移。
需求来源：《Day_plan/Day2_3D康伴数字人.md》第 5 章与《TDD》6.3 节。
相关现状：数据库现有 11 张表，无任何账号/Token 表。

【Task 任务】
整理"三张授权关联表（building_assignments / doctor_elder_assignments / family_elder_links）"
的需求：字段、约束、唯一性、删除策略，并指出 Day2 文档与 TDD 6.3 的差异。

【Constraints 约束】
- 只做澄清，不写代码不建迁移；
- staff_tokens、audit_logs 等其他后续表一律不得混入；
- 结论注明出处章节。

【Expected Result 预期结果】
《需求复述》《歧义与冲突清单》《待我决策的问题》三节；我答复前不得动手。
```
