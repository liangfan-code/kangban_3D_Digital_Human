# 模板 05：调试报错

> 用途：报错或行为不符预期时，让 AI 先定位根因、提出修复方案，**确认后最小修复**，禁止大改重构。

## 模板正文

```
【Context 背景】
项目：康伴 3D 数字人康养陪伴系统。
环境：{Python 版本 / 本地库 / 相关依赖版本}。
预期行为：{依据文档}。
实际行为：{现象描述}。

【Task 任务】
1. 根据以下证据定位根因（复现命令、完整报错、相关日志）：
   {粘贴报错/日志/复现步骤}；
2. 给出根因分析链（证据 → 推断 → 结论）；
3. 提出最小修复方案（不扩大改动面），并列出修复后验证命令。

【Constraints 约束】
- 先给根因分析和方案，等我确认后再改代码；
- 修复只动根因相关代码，禁止顺手重构/改格式；
- 禁止靠删除断言、跳过测试、放宽校验来"让测试变绿"；
- 每次修改后必须给出实测输出，不写"应该通过"。

【Expected Result 预期结果】
《根因分析》（证据链）→《修复方案》（diff 预览）→（确认后）《实测结果》。
若证据不足以定位，列出还需要我提供的证据清单，不得猜测后乱改。
```

## 本项目示例

```
【Context 背景】
项目：康伴 3D 数字人康养陪伴系统，Day2。
环境：Python 3.13 (.venv)、PostgreSQL 17 (Docker kangban-pg，端口 5433)、kangban_test 测试库。
预期行为：python -m pytest 全绿（Day2 文档 6.4 节）。
实际行为：tests/test_auth_login.py 中"错误密码 401"用例返回 500。

【Task 任务】
定位 500 根因。证据：
- 复现：python -m pytest tests/test_auth_login.py -k wrong_password
- 报错：{粘贴完整 traceback}
- 服务端日志：{粘贴该请求的结构化日志（含 trace_id）}

【Constraints 约束】
- 先分析后动手；修复最小化；
- 不得放宽登录校验逻辑来消除报错；
- 修复后给出该用例与全量 pytest 的实测输出。

【Expected Result 预期结果】
根因分析（含证据链）→ 修复 diff → 实测：单用例通过 + 全量测试通过数。
```
