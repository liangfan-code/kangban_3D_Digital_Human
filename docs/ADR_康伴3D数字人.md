## ADR-001 使用 PostgreSQL + pgvector 作为统一主数据平台

- 状态：已接受
- 日期：2026-11-03

### 背景

项目同时需要业务事务、权限关系、长期记忆向量、声纹向量和 LangGraph Checkpoint。第九章出现 MySQL 课程能力映射，但系统架构和部署章节明确使用 PostgreSQL + pgvector。

### 决策

主数据库采用 PostgreSQL，向量能力采用 pgvector，ORM 使用 SQLAlchemy 2.x，迁移使用 Alembic；不同时引入 MySQL。

### 备选方案

MySQL + 独立向量数据库：运维组件更多，身份过滤和事务一致性更复杂。

### 影响

优点是减少数据平台数量并支持统一迁移；代价是需要 PostgreSQL/pgvector 环境。Embedding 模型确定前不固定向量维度和 ANN 索引。

## ADR-002 采用单仓库、模块化单体，而非 MVP 微服务

- 状态：已接受
- 日期：2026-11-03

### 背景

项目包含 HTTP、WebRTC、Agent、工作流、调度、多个后台和 MCP，但教学周期只有 10 天，团队规模有限。

### 决策

使用一个 Git 仓库和模块化 FastAPI 后端；平板前端、简单后台、MCP Server 和模型服务按需要独立运行，但不在 MVP 拆分业务微服务。

### 备选方案

全量微服务：独立部署清晰，但网络、鉴权、观测和运维成本过高。

### 影响

降低联调和部署成本。模块间必须通过明确服务边界协作，禁止跨层直接操作数据库或绕过权限。

## ADR-003 使用安全优先的三级路由与一个受约束主控 Agent

- 状态：已接受
- 日期：2026-11-03

### 背景

所有请求都调用大模型会增加延迟和成本；纯规则/分类器又无法处理复杂多工具请求。多个自由 Agent 会增加权限和编排不确定性。

### 决策

采用“安全判断 → 规则层 → System One → CompanionAgent”的级联结构。规则处理固定指令，System One 处理结构化快决策，只有一个受约束 CompanionAgent 处理复杂 ReAct 请求。

### 备选方案

1. 全量大模型：简单但慢且贵。
2. 纯分类路由：可控但无法处理开放域和多步骤任务。
3. 多个自由 ReAct Agent：职责看似清晰，但调用链和权限难控制。

### 影响

简单请求可短路，复杂请求保留推理能力。必须记录路由层级、置信度、Tool 次数和成本；敏感判断始终优先，不被普通分类覆盖。

## ADR-004 仅对有状态长流程使用 LangGraph

- 状态：已接受
- 日期：2026-11-03

### 背景

健康检查和普通对话主链路主要是直线流程；用药和健康事件存在循环、分支、恢复、HITL 和副作用。

### 决策

直线请求使用 FastAPI/确定性代码；用药确认与健康事件使用 LangGraph 子图；Checkpointer 使用 PostgreSQL，与主数据平台保持一致。

### 备选方案

1. 所有流程都上图：增加简单链路复杂度。
2. 全部手写 if-else：状态分散，恢复和人工暂停难验证。
3. SQLite Checkpoint：适合本地演示，但与统一 PostgreSQL 部署目标不一致。

### 影响

状态、节点和分支可测试、可恢复。图状态必须包含决策依据和副作用结果，HITL 前后需要独立测试。

## ADR-005 身份采用四级级联，可信身份只存在 Runtime Context

- 状态：已接受
- 日期：2026-11-03

### 背景

长者在单人间和双人间使用共享房间设备，身份错误会泄露记忆、健康和用药信息。模型或客户端提交的 `elder_id` 不可信。

### 决策

身份按“设备绑定 → 房间候选 → 声纹 → 主动确认/护工临时授权”级联；成功后注入 Runtime Context。失败进入不带个人记忆的通用模式。

### 备选方案

只依赖声纹：误识和拒识会直接影响隐私与可用性。只依赖设备：双人间无法区分住户。

### 影响

单人间以设备绑定为主，双人间必须额外确认。所有会话、记忆和 Tool 都使用服务端身份，攻击测试成为发布门禁。

## ADR-006 外部工具通过 MCP 封装

- 状态：已接受
- 日期：2026-11-03

### 背景

天气、HIS 和微信等外部能力需要在不修改主 Agent 的情况下替换厂商，并统一权限、审计和测试。

### 决策

外部 Tool 优先封装为 MCP Server；主控 Agent 通过 MCP 客户端发现和调用。MVP 的 HIS、微信均使用 mock。

### 备选方案

在每个业务模块直接写 HTTP 客户端：初期简单，但工具协议、权限和替换成本会逐渐失控。

### 影响

工具边界统一。每个 Server 必须定义 schema、鉴权、超时、幂等、上下文隔离和审计；传输方式待 POC 后确定。

## ADR-007 实时语音使用 WebRTC，3D 使用现成 VRM

- 状态：待验证
- 日期：2026-11-03

### 背景

产品需要低延迟全双工语音、主动外呼和口型同步，但项目不做图形学或自研媒体基础设施。

### 决策

语音链路使用 WebRTC + aiortc + 流式 ASR/TTS；前端使用现成 VRM 与 `@pixiv/three-vrm`，通过 viseme 或近似映射驱动口型。连接失败降级为文字聊天。

### 备选方案

普通 HTTP 轮询：实现简单但实时性差。Live2D/高精度建模：不符合既定形象和范围决策。

### 影响

需要处理 STUN/TURN、异步事件循环、首包延迟和浏览器安全上下文。POC 未通过前不承诺端到端延迟。

## ADR-008 长期状态、短期状态和向量记忆分责存储

- 状态：已接受
- 日期：2026-11-03

### 背景

业务事务、短期会话和长期记忆具有不同的一致性、生命周期和访问方式。

### 决策

PostgreSQL 保存业务数据、授权、审计、长期记忆和 Checkpoint；Redis 保存短期对话状态、限流和重复调用检测；原始音频只进入有时限的临时存储。

### 备选方案

全部放 Redis：持久化和授权查询不足。全部放 PostgreSQL：高频临时状态和限流实现较重。

### 影响

必须明确每类数据的唯一权威来源、过期策略和恢复方式；Redis 丢失不得造成长期业务记录丢失。

## ADR-009 高危副作用默认不自动执行，必须 HITL

- 状态：已接受
- 日期：2026-11-03

### 背景

误识别、误转写或错误分级可能触发通知、医院对接或紧急工单，自动执行会放大风险。

### 决策

敏感意图优先短路；高危副作用进入 LangGraph Interrupt/HITL。确认前无副作用，确认后按权限、幂等和审计规则执行。

### 备选方案

完全自动化：延迟低但不可接受地放大误报和越权风险。

### 影响

增加人工处理步骤，但获得可控性。必须测试绿色不建单、黄色陪护确认、红色医生确认，以及重复确认不重复执行。

## ADR-010 平板与简单后台采用不同前端复杂度

- 状态：已接受
- 日期：2026-11-03

### 背景

平板需要 VRM 和 WebRTC，护工/医生/家属/运营页面主要是列表、详情、确认和简单图表。

### 决策

平板保留必要前端构建和 3D 依赖；其他端优先简单 HTML+JS 或服务端渲染，家属只做移动 H5，不开发原生 App。

### 备选方案

所有端统一重型 SPA：技术一致但增加构建、依赖和无障碍适配成本。

### 影响

降低重复页面的实现成本。必须分别验证平板实时状态、后台权限和家属 375px 移动布局。

## ADR-011 可观测和评测是主链路组成部分

- 状态：已接受
- 日期：2026-11-03

### 背景

系统包含多级路由、模型、Tool 和人工节点，仅靠最终回答无法定位延迟、成本和错误来源。

### 决策

从 Day1 建立 `trace_id`，后续以 Logs、Metrics、Traces、Langfuse、`decision_logs` 和固定评测集构成观测与评测闭环。

### 备选方案

项目末期再补监控：难以还原早期基线和失败原因。

### 影响

所有关键节点需要打点和版本记录。指标必须可复算，bad case 必须回流；日志不得记录未脱敏敏感信息。

## ADR-012 配置统一进入 Settings，密钥只使用安全占位与环境注入

- 状态：已接受
- 日期：2026-11-03

### 背景

项目涉及数据库、模型、ASR/TTS、声纹、JWT、WebRTC 和 Langfuse 等多类配置，且 Day1 不应依赖真实外部密钥。

### 决策

`.env.example` 区分 Day1 基础配置和后续预留配置；后续字段在 Settings 中为 Optional，对应阶段启用时才做必填校验。真实密钥不进入 Git、Prompt、镜像或日志。

### 备选方案

各模块直接读取环境变量：配置分散，启动校验和文档难统一。Day1 强制所有密钥必填：无法离线启动骨架。

### 影响

骨架可无外部服务启动，后续接入时有统一配置入口。README 必须明确各阶段配置要求。

## ADR-013 Day1 固定 11 表基线，后续业务表通过新迁移演进

- 状态：已接受
- 日期：2026-11-03

### 背景

Day1 要求一次设计 11 张基础表，但登录授权、用药确认、日报、健康事件、审计和指标等业务无法仅靠这 11 表完整表达。

### 决策

Day1 保持 11 表基线和两次初始迁移；后续根据 PRD/TDD 评审新增账号授权、设备凭证、用药事件、决策日志、媒体历史、健康事件、日报、家属签到与关怀、礼包规则与发放、审计和指标等表，不伪造外键，不回改已执行主迁移。

### 备选方案

1. Day1 擅自增加全部表：扩大当天范围且未经业务评审。
2. 永远只使用 11 表：会导致登录、确认、日报和审计语义丢失或挤入不合适的 JSON 字段。

### 影响

兼顾 Day1 验收与完整业务演进。每个后续迁移必须回链需求、更新 ER/TDD 并人工审查。

## ADR-014 模型与供应商通过适配器和 POC 决定，不提前锁死

- 状态：待验证
- 日期：2026-11-03

### 背景

DeepSeek/Qwen、Chinese-Jev/Laya、Embedding、ASR/TTS 的具体可用性、成本、延迟和许可证需要实际验证。

### 决策

先定义统一接口、配置和评测方法，再通过 POC 选择具体模型与供应商。System One 必须可本地部署；System 2 通过兼容 API 适配；向量维度在 Embedding 确定后固定。

### 备选方案

在设计阶段直接锁定全部厂商：可能因安装、网络、成本或许可证问题返工。

### 影响

避免过早绑定，但要求适配器测试和版本清单。任何替换都必须重跑相关评测，不得只修改模型名称。

## ADR-015 方言语音采用官方 ASR/TTS API 与可选规范化，不接管项目对话

- 状态：待验证
- 日期：2026-11-03

### 背景

部分长者更习惯方言，直接要求使用普通话会降低陪伴和关键业务确认的可用性。网页版对话产品虽然可能支持方言，但自动操作网页、让外部模型自由回答会绕过项目身份、安全、HITL、审计和数据边界。豆包/火山引擎等服务的具体方言、流式能力、延迟和成本尚未验证。

### 决策

首版选择一种目标方言，通过官方 ASR/TTS API 适配器接入现有 WebRTC 和受控对话链路。保留原始转写、规范化文本、方言类型和各级置信度；仅在评测证明需要时增加语义规范化。药名、剂量、数值、时间和否定词低置信或发生变化时必须复述确认，不得直接执行用药、健康或敏感事件副作用。方言失败时降级为普通话语音或文字。

### 备选方案

1. 自动操作网页版对话产品：接入看似快速，但会话、权限、工具和数据流向不可控，不采用。
2. 让外部对话模型直接生成业务回答并操作工具：绕过三级路由和 HITL，不采用。
3. 所有方言文本固定再调用一次大模型规范化：增加延迟、成本和改写风险，只在必要场景按评测启用。
4. 自研方言 ASR/TTS：超出 MVP 教学周期和项目边界。

### 影响

方言只是语音与文本适配能力，不改变身份、路由和副作用规则。POC 必须使用 30–50 条覆盖普通对话和关键语义的教学语料，输出 bad case、延迟、TTS 可理解度和降级报告；未通过前不承诺识别准确率或端到端方言能力。

## ADR-016 家属关怀采用累计签到、真实关怀行动与幂等礼包

- 状态：已接受
- 日期：2026-11-03

### 背景

家属签到可以促进持续关怀，但连续签到清零会制造形式化压力，仅靠点击又可能变成无效打卡。重复请求、多家属同日和并发发奖可能破坏权益一致性；若把礼包与更多健康或对话数据绑定，会扩大隐私风险。

### 决策

采用按社区本地日期计算的累计签到，每位长者每日最多一条有效奖励签到，漏签不清零。语音、照片、问候、通话和线下探望等关怀行动独立记录，是否计奖由版本化规则决定。使用 PostgreSQL 事务、唯一约束和幂等键保证同一规则版本只发一次、线下核销不重复执行。礼包不扩大任何数据权限，MVP 不接支付采购。

### 备选方案

1. 连续签到、中断清零：规则简单但有惩罚性，容易诱导形式化签到，不采用。
2. 只保存家属账号的连续点击次数：无法防止多位家属同日刷取，也无法表达真实关怀，不采用。
3. 用额外健康、记忆或对话内容作为奖励：混淆权益与授权，不采用。
4. 接入真实电商或支付履约：超出 MVP 范围，不采用。

### 影响

后续需新增 `family_checkins`、`family_care_activities`、`reward_rules`、`reward_grants`，但不回改 Day1 的 11 表基线。服务端负责日期、关联校验、计数和状态迁移；必须测试跨家属越权、同日重复、跨天累计、漏签、并发发奖、重复核销及奖励前后权限不变。累计天数 N、礼包内容和有效期由运营评审配置。

## ADR-017 健康档案采用数据分级、独立 ACL 与受限 AI 解读

- 状态：已接受
- 日期：2026-11-05

### 背景

Day2 健康档案需要同时服务护工（日常护理够用）、医生（全量诊疗）、家属（适度知情）三类角色，而"重大疾病"等记录一旦被护工或未授权家属看到即构成隐私泄露。若只靠角色名放行，无法表达"同角色不同人不同授权"；若把 AI 解读的原始病历交给外部大模型，会扩大出域风险。

### 决策

1. 档案按五类纵向记录（`elder_health_records`），`major` 类服务端强制 `data_level=confidential`，不信任客户端传入分级。
2. 访问控制三层叠加：角色范围判定（范围外 404 隐藏存在性）→ `health_grants` 独立 ACL（管理员逐人配置"账号 × 长者 × 查看/编辑 × basic/confidential"，编辑位必须含查看位，软吊销可恢复）→ 查询层数据分级过滤。护工在任何路径下都不可见 confidential 级记录。
3. 全部写操作进入只增不改的 `health_audit_logs`（旧值→新值快照），审计仅管理员可查。
4. AI 解读作为正式功能但严格受限：仅 family/admin 且持 basic 查看位可发起；出域白名单只含 basic 级去标识条目；服务端固定提示词模板（prompt_version 留档）；每小时 1 次频控；未配置 503、超限 429、失败 502 不留档；输出固定附免责声明，不做诊断。
5. LLM 通过 OpenAI 兼容适配器接入（环境变量注入 Base URL/Key/Model），已实测 DashScope 兼容模式连通；最终供应商仍由 POC-08 复核，替换模型不改变本 ADR 的边界。

### 备选方案

1. 仅按角色放行：实现简单，但无法表达逐人授权差异，护工会看到重大疾病，不采用。
2. 复制数据到"家属视图表"：数据双写易失真，且无法保证 confidential 不被复制泄漏，不采用。
3. 让外部 LLM 直接访问数据库或全量档案换取更好的解读质量：出域与越权风险不可接受，不采用。
4. AI 解读仅做演示不落库：无法审计解读历史与责任归属，不采用。

### 影响

- 数据库通过迁移 0005 新增五表（档案/ACL/审计/AI 快照/摘要），不回改已执行迁移（ADR-013）。
- ACL 判定逻辑成为安全门禁的一部分，必须覆盖"范围外 404、无 ACL 403、分级过滤、编辑位含查看位、护工不可见 confidential、AI 出域白名单"的攻击路径测试（并入 POC-05 范围）。
- 模型服务不可用时功能整体降级关闭（公开 `/config/flags` 开关），不换用不受控通道。
- 医生健康摘要（`health_summaries`）版本自增、家属已阅回执幂等，为后续家属日报功能提供可复用的摘要与回执模式。

## ADR 使用与变更规则

1. PRD 改变业务目标时，检查相关 ADR 是否仍成立。
2. 修改 ADR 已接受的决策时，新增替代 ADR 或追加“被替代”状态，不静默删除历史理由。
3. POC 可以确认或推翻“待验证”决策，结果必须同步到 TDD、依赖、配置和测试。
4. AI Agent 不得自行改变这些决策；发现冲突时应先列出受影响的 PRD、TDD、ADR 条目并请求评审。
5. 代码评审应检查实现是否违反 ADR，尤其是身份、HITL、数据隔离、MCP、Checkpoint 和密钥规则。

## ADR-018 实时语音 Provider 选型：FunASR 本地镜像 + Edge-TTS + sherpa-onnx，经适配器接入

### 背景
POC-01/02（Day3）实测：aiortc WebRTC 本地回声通过；FunASR 流式 ASR 说完→最终转写 242ms（≤1s 达标）；Edge-TTS 首包基线 1331ms。ADR-014 要求厂商由 POC 决定、不提前锁死。

### 决策
ASR 采用 FunASR 官方实时识别镜像（本地 Docker，`compose.funasr.yaml`）；TTS 采用 Edge-TTS（云端合成，PyAV 解码 16k，免 ffmpeg 系统依赖）；声纹采用 sherpa-onnx CAMPPlus（192 维）+ TEN-VAD。三者均通过 `app/integrations/` 的 Provider 抽象接口接入，可替换。

### 备选方案
云端商用 ASR/TTS API（未选：教学内网成本与配额不可控，且方言供应商待 POC-10）；浏览器端 Web Speech API（未选：无声纹门控配合、兼容性弱）。

### 影响
FunASR 镜像 offline 阶段结果不带 `is_final` 字段（以 `mode` 含 `offline` 判定终句），且置信度恒 0（前端显示"—"）；Edge-TTS 依赖外网（不可用时语音链路整体降级，停 FunASR 容器亦可演示降级通道）；均为已记录的已知限制。

## ADR-019 声纹向量入 pgvector，临时验证 Token 仅内存 300s

### 背景
四级身份级联（ADR-005）的第三级「声纹」需要落地；POC-04 双人间链路提前至 Day3 实测（相似度 0.5652/0.6786/0.6044，阈值 0.55）。

### 决策
声纹 embedding（192 维）写入 Day1 既有的 `voiceprints` 表（pgvector，`status=active`，`embedding_model` 记录模型名）；验证通过后签发 300s 临时验证 Token，仅存进程内存（`voice_token_store` 模块单例），重启即失效，不新增表、不落库。

### 备选方案
Redis 存储临时 Token（未选：Day3 不引入 Redis 依赖，内存单例在教学单进程部署下等价）；文件存声纹（未选：ADR-008 已定统一 pgvector）。

### 影响
- 已知边界：embedding 明文存储（TDD §6.4 的「声纹 embedding 加密」与 ER「加密方案待 POC」仍未实现，留 Day8 复核）；
- 多进程/多副本部署时内存 Token 不共享，需换 Redis（正式部署前评审）；
- 会话内声纹快照过期问题由 `embedding_reloader` 现场重查解决，录入后免重连生效。

## ADR-020 登录页「老人生物识别进入」为教学演示后门，受环境开关控制

### 背景
长者无法记忆/输入设备 Token，产品需要适老免输入进入；但 elder 页全部接口要求真实设备 JWT，纯前端模拟无法签发凭证。Day3 晚应用户需求实现。

### 决策
登录页新增「老人生物识别进入」：选房间号 → 指纹（无硬件，点击图标即进，仅教学演示）或声纹（真比对 Day3 CAMPPlus 声纹库，阈值 0.55）。后端提供 2 个公开演示接口（`GET /voice/biometric/rooms`、`POST /voice/biometric/login`），全部挂 `BIOMETRIC_DEMO_ENABLED` 开关（默认开）；指纹「点击即进」等同登录后门（知道房间号即可进入长者页，绕过设备 Token），声纹模式为真实验证。

### 备选方案
纯前端模拟（未选：无法签发真实 JWT，进入 elder 页即 401）；每次演示前手工签发注册凭证（未选：凭证 24h 过期，实操不可持续）。

### 影响
- 安全边界：开关开启期间存在「房间号即凭证」的演示后门；答辩/对外演示结束后应置 `BIOMETRIC_DEMO_ENABLED=0`（接口 403 + 前端入口隐藏），恢复严格鉴权；
- 不新增任何表、不改 auth 高风险区（设备 Token 签发复用 `issue_access_token`）；
- 声纹模式与正式声纹门控共用同一声纹库与阈值，后续正式身份体系收敛时此入口可直接关闭，不影响既有链路。

## ADR-021 上下文会话状态用 PostgreSQL 替代 Redis，更早历史摘要留 Day7 记忆治理

日期：2026-11-06（Day4 收尾）

### 背景
大纲课时 4.4 要求「最近 5 轮原文 + 更早历史摘要 + 会话状态存 Redis」。Day4 实际实现为：`conversation_messages` 表（迁移 0006）按 `(thread_id, seq)` 落库全部对话，回复链取最近 5 轮原文注入 system prompt；长历史无摘要。

### 决策
1. Dev/POC 阶段**不引入 Redis**：会话状态与历史统一存 PostgreSQL（本项目单体 + 本地单实例部署，Redis 的低延迟优势无消费场景，多一个有状态组件反而增加容器编排与持久化负担，与 ADR-001「PostgreSQL 统一主数据平台」一致）；
2. 「更早历史摘要」**留 Day7 记忆治理**一并实现：摘要生成依赖 LLM 总结链路与 `memories` 表设计（大纲 Day7 记忆召回/冲突/遗忘），届时摘要与记忆治理共用同一套基础设施，避免 Day4 重复建设后 Day7 重构。

### 备选方案
按大纲字面引入 Redis + 当日实现摘要（未选：单实例场景无收益；摘要基础设施 Day7 才有，当日只能做一次性 hack）。

### 影响
- Day4 验收口径：4.4 的「最近 5 轮 + prompt 入 Git + LLM 接入送 TTS」已实测；「Redis 可见会话状态」以「psql 直查 conversation_messages」等效替代（92 行成对落库）；
- Day7 实施时需新增：摘要生成任务（LLM 总结超窗历史 → 摘要注入 prompt）、触发阈值（如历史 >20 轮）；
- 若 Day8+ 出现多实例部署或高频写入场景，再评估引入 Redis（届时本 ADR 作废重立）。
