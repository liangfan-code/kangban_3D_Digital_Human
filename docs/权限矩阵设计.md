# 权限矩阵设计文档（阶段一 · v1.0 评审稿 ｜ Day2 健康档案 v2.0 增补）

> 状态：**待评审**。本文档只做设计，不含代码。评审通过后作为 1.2 管理 API、1.3 CLI、2.2 前端渲染的唯一权限依据。
>
> **v2.0 增补（2026-11-05，Day2 健康档案）**：新增 §2.9 健康档案、§2.10 健康授权与审计、§2.11 AI 分析出域白名单；§7 补健康相关接口清单。健康信息采用「范围判定 → ACL 授权（health_grants）→ 数据分级」三层模型：admin 恒全量；护工/医生/家属必须经管理员在 health_grants 显式放权方可读写，且 `category=major`（重大疾病）一律 `data_level=confidential`（服务端派生，护工不可见，家属/医生需显式授予隐私位）。
>
> 已确认决策（2026-11-04）：
> 1. **push 口径**：每阶段验收通过后执行一次 push（阶段一验收后 push、阶段二验收后 push），其余时间仅本地小步提交。
> 2. **DELETE /elders/{id}**：软删，status 置 `discharged`（退住），同时清空 `room_id`/`bed_no` 释放床位（见 §4 说明，需随本矩阵一并确认）。
> 3. **rooms/personas/devices 删除**：全部软删（rooms→`inactive`、devices→`retired`、personas→`is_active=false`），不物理删除。
> 4. **账号管理**：admin 可管理包括其他 admin 在内的全部账号；**不提供物理删除**，仅停用/启用/重置密码；**最后一个 active 管理员不可停用**（防锁死，409）。

## 1. 角色定义

| 角色 | 载体 | 通行凭证 | 范围依据 |
| --- | --- | --- | --- |
| admin 管理员 | 人账号 | 人 JWT（60 分钟） | 恒通过（全量数据） |
| nurse 护工 | 人账号 | 人 JWT | building_assignments（active 楼栋集合） |
| doctor 医生 | 人账号 | 人 JWT | doctor_elder_assignments（active 且未过期） |
| family 家属 | 人账号 | 人 JWT | family_elder_links（active 且未过期） |
| 老人（=房间平板设备） | 设备（无账号） | 设备 Token（90 天） | 仅本设备绑定房间，仅 /devices/me |

不变式（ADR-005/008）：人/设备 Token 严格互斥，互调一律 403；`elder_id` 一律由服务端上下文注入，不信任客户端传参；老人无账号密码。

### 2.11 AI 一键健康分析出域白名单（v2.0 新增）

| 项 | 规则 |
| --- | --- |
| 触发角色 | 仅 family / admin（`require_role("family","admin")`）；护工/医生调用 403 |
| 授权前提 | 需对该长者有 basic 查看位（viewer_level ≠ None），否则 403 |
| **出域数据白名单** | 仅 basic 级四类记录的 `item_key + value_text`；**confidential（major/重大疾病）一律在服务端剔除后才拼提示词，永不出库** |
| 提示词约束 | 服务端模板固定（prompt_version 留档）：输出清晰简短、直指问题症状、给改善建议，禁止冗长（呼应家属端阅读负担要求） |
| 降级语义 | 未配置 LLM → 503（前端按钮置灰：公开 GET /config/flags 返回 `ai_analysis_enabled`）；触发频控 → 429；LLM 调用失败 → 502 且**不留档** |
| 留档字段 | analysis_text / model_name / prompt_version / requested_by；历史回看同样仅 basic 级内容 |
| 红线 | AI 输出不作为诊断依据（仅健康信息解读），不替代 SOS；不把长者身份信息（姓名/房间）送出域 |

## 4. 软删口径汇总（本次全部 DELETE 的统一语义）

| 资源 | 软删动作 | 前置校验 | 恢复方式 |
| --- | --- | --- | --- |
| rooms | status→inactive | 房间内无 active 长者、无 active 绑定设备，否则 409 | PUT 改回 active |
| personas | is_active→false | 无强制；已引用长者保留（换绑/新建时校验拒绝） | PUT 置 true |
| devices | status→retired | 无强制 | 无恢复接口（退役终态）；可新建设备替代 |
| elders | status→discharged，清空 room_id/bed_no | 无强制 | PUT 可改回 active（改回时重新走床位校验，room_id/bed_no 需重新成对提供） |
| accounts | 不提供删除；停用 disabled | 最后一个 active admin 禁止停用 409 | enable |

> elders 清空床位说明：若保留 room_id/bed_no， discharged 长者仍占用床位校验（`_validate_placement` 查占用不分状态），新长者无法入住该床，语义错误。故退住同时释放床位。此项随本矩阵一并确认。

## 5. 设备激活缺陷修复方案（1.2 范围内）

**现状**：`register_device`（[app/services/device.py](../app/services/device.py) L104-134）换发长期 Token 后未改 `devices.status`，设备停留在 `pending`；而 `validate_device_token` 要求 `device.status == active` → 设备 Token 有效却永远 401。

**修复**：`register_device` 中 `consume_register_token` 成功后、commit 前，将 `device.status = DeviceStatus.ACTIVE`（幂等：已是 active 不变）。

**测试**：① 注册成功后回查库 `devices.status == active` 且 `/devices/me` 200；② 处于 pending 的设备（手工构造有效 Token）调 `/devices/me` 返回 401。

| 接口 | 设备 Token | 人 JWT（护工/医生/家属） | 管理员 JWT | 未认证 |

| `POST /api/v1/voice/biometric/login` | — | — | — | ✅ 公开（同上；指纹=演示直进，声纹=真比对阈值 0.55；无活跃设备房间 409） |

补充语义：

1. WS 与 REST 双凭证互斥沿用既有约定：同一连接内设备 Token 与人 JWT 不混用。
2. 声纹验证通过仅签发 300s 临时验证 Token（仅内存），不改变设备/人 Token 体系；失败进入通用模式（不带个人记忆），不阻断会话。
3. 生物识别演示接口是**唯一**的未认证写能力入口（签发真实设备 JWT），属教学演示后门（ADR-020）：`BIOMETRIC_DEMO_ENABLED=0` 时整体关闭，指纹「点击即进」随之失效。
4. 设备注册凭证（一次性 token_urlsafe）与设备 JWT、声纹临时 Token 三者严格区分，混用一律 401/4403。
