## 1. 产品背景与定位

康伴是部署在 CCRC 康养社区长者卧室平板上的 3D 数字人陪伴系统。

系统通过 WebRTC 全双工语音与长者交流，提供情感陪伴、用药提醒、健康采集、戏曲/影视娱乐和信息搜集服务。

机构是主要付费方，长者是主要使用者，护工、医生、家属和运营管理员通过各自视图使用相关数据。

产品优先解决用药漏服、护理重复劳动、健康数据断档和家属信息不对称，3D 形象与娱乐功能用于增强体验，不替代核心护理闭环。

### 2.3 方言 与 家属关怀观察指标

- 方言语音：分场景统计 转写置信度、药名/剂量/数值/时间/否定词 bad case、复述确认率、方言 TTS 可理解度、各阶段延迟和降级次数。
- 家属关怀：在既有日报打开率之外，观察有效签到、语音/照片/问候/通话/线下探望记录、礼包解锁与核销，以及长者满意度反馈。
- 首版只建立 可复算基线，不在没有样本和测量方法时 虚构提升比例或数值目标。

## 3. 用户角色与权限概要

| 角色 | 核心诉求 | 主要权限 |
| --- | --- | --- |
| 长者 | 被陪伴、被记住、按时吃药、减少麻烦 | 个性化对话、查看本人健康信息、确认用药、发起求助、申请删除个人数据 |
| 同房长者 | 使用房间设备 但不被误认 | 不查看他人记忆和健康信息；身份不清时 进入隐私收敛或通用模式 |
| 护工 | 减少重复提醒，及时处理异常 | 查看负责范围工单和健康信息、处理告警、按权限调整用药计划、协助身份确认；经健康授权可查看/编辑负责楼栋长者的 basic 级健康档案，任何路径不可见 confidential 级（重大疾病）记录 |
| 医生 | 获取连续健康数据 | 查看负责长者健康趋势、复核健康事件、按权限调整 用药计划；经健康授权可查看/编辑 basic 与 confidential 全量健康档案，并生成版本化健康摘要 |
| 家属 | 了解并关怀 长者日常状态 | 仅查看本人关联长者的日报摘要；可为关联长者签到、记录关怀行动和查看礼包进度，不查看完整对话和个人记忆；经管理员逐人授权后可查看关联长者的健康档案与医生健康摘要，并在授权与频控约束下发起 AI 健康解读 |
| 运营管理员 | 管理设备、人设、关怀活动和使用情况 | 配置设备、人设、形象、长者档案和礼包规则；执行授权线下核销；审计敏感数据删除；配置健康授权矩阵（账号 × 长者 × 查看/编辑 × basic/confidential）并查阅健康审计流水 |

所有数据访问还需经过角色、负责范围和长者关联关系校验，不能只凭角色名称放行。

## 4. 需求故事

### US-01 用药提醒与确认

**作为**容易忘记服药的长者，**我希望**数字人到点主动提醒我并让我口头确认，**以便**减少漏服和重复服药。

验收要点：

- 到点主动外呼，提醒包含正确药品和剂量。
- 长者回答“吃了”后记录确认；回答“没吃”或无应答时按规则重试。
- 最多重试三次，仍失败则创建漏服工单。
- 服务重启后待确认状态不丢失。

### US-02 漏服工单处理

**作为**夜间值班护工，**我希望**只收到负责楼栋的异常工单，**以便**优先处理真正需要 人工介入的情况。

验收要点：护工看不到其他楼栋工单；可确认、处理和关闭工单；状态变化有审计记录。

### US-03 有记忆的陪伴对话

**作为**长者，**我希望**数字人记得我的称呼、喜好和家庭情况，**以便**获得连续、自然的陪伴体验。

验收要点：新会话可召回有效偏好；不同长者记忆严格隔离；冲突记忆可标记替代；医疗问题不做诊断。

### US-04 健康采集与医生复核

**作为**合作医生，**我希望**查看连续、结构化的健康记录和异常事件，**以便**提高每周查房质量。

验收要点：采集血压、睡眠、情绪和主诉；正常数据入库；异常按绿/黄/红分级；高危副作用在人工确认前不得执行。

### US-05 家属日报

**作为**异地家属，**我希望**每天收到简明语音日报，**以便**了解长者的基本状态。

验收要点：日报仅含授权摘要，不暴露完整病历、原始对话或他人信息；H5 适配手机并可播放语音。

### US-06 娱乐点播

**作为**喜欢戏曲和老电影的长者，**我希望**通过语音点播和调整播放，**以便**无需打字或复杂操作。

验收要点：可按剧种、年代和题材检索；“换一段、停、大声点”直接命中规则；只播放授权、教学或公有领域资源；记录观看历史用于推荐。

### US-07 敏感事件人工接管

**作为**出现胸痛、跌倒或情绪危机的长者，**我希望**系统及时通知人工，**以便**避免错误回复延误处理。

验收要点：敏感意图一票否决；不进入开放域大模型生成建议；播放预设安抚话术并进入人工确认队列；不替代 SOS。

### US-08 设备与人设配置

**作为**运营管理员，**我希望**配置设备与房间绑定、长者档案和数字人人设，**以便**让平板提供正确的个性化服务。

验收要点：设备绑定可追溯；人设可配置称呼、性格、形象和音色；无权限角色不能修改。

### US-09 双人间隐私保护

**作为**双人间长者，**我希望**系统先确认我是谁，**以便**避免听到或泄露同房者信息。

验收要点：声纹达到阈值才锁定身份；失败时主动询问；仍失败则进入不带个人记忆的通用模式；重叠语音不硬猜说话人。

### US-10 故障降级

**作为**长者，**我希望**语音或模型服务异常时仍能知道发生了什么，**以便**避免面对白屏或无响应。

验收要点：ASR/TTS、LLM、WebRTC、System One 和媒体服务均有明确降级路径、提示话术与日志。

### US-11 方言语音交流

**作为**习惯使用方言的长者，**我希望**数字人能听懂并用我熟悉的方式回答，**以便**自然完成陪伴、娱乐和生活信息请求。

验收要点：

- 优先选择一种目标方言完成官方 ASR/TTS API 验证，保留原始转写、规范化文本、方言类型和各级置信度。
- 普通对话可按评测结果使用可选语义规范化；方言能力仍经过原有身份、安全、路由和 HITL 链路。
- 用药、健康和敏感求助中的药名、剂量、数值、时间、否定词置信度不足时必须复述确认，不得直接执行。
- 方言识别或朗读不可用时降级为普通话语音或文字，并给出明确提示，不出现白屏或无响应。

### US-12 家属累计签到与关怀礼包

**作为**异地家属，**我希望**通过累计签到和真实关怀行动为长者解锁礼包，**以便**持续表达关心而不是只在日报中被动查看。

验收要点：

- 服务端按社区本地日期记录每位长者每天最多一次有效奖励签到；重复操作返回同一结果，漏签不清空累计进度。
- 可记录语音、照片、问候、通话和线下探望等授权关怀行动，关怀记录与奖励签到分别保存。
- 达到运营配置的累计天数后只解锁一次对应礼包；家属可查看进度和状态，礼包不包含额外健康、记忆或对话数据权限。
- MVP 由授权运营人员线下核销，重复核销不重复执行；跨家属访问、伪造长者或日期、越权核销均被拦截并留审计。

### US-13 健康档案分级记录与授权访问

**作为**合作医生与值班护工，**我希望**长者的健康档案按类别纵向记录并按数据密级授权访问，**以便**护理工作够用、隐私信息不外泄。

验收要点：

- 健康档案按"体征 / 身体部位 / 当前用药 / 慢性病 / 重大疾病"五类逐条记录；重大疾病类服务端强制为 confidential 级。
- 访问控制三层叠加：负责范围判定（范围外 404 隐藏存在性）→ 健康授权 ACL（管理员逐人配置"账号 × 长者 × 查看/编辑 × basic/confidential"）→ 数据分级过滤（无相应级别授权不可见）。
- 护工任何路径不可见 confidential 级记录；编辑授权必须包含对应查看授权，否则请求被拒绝。
- 档案的新建、修改全部留审计流水（旧值→新值），审计仅管理员可查。
- 护工端提供"今日待录入体征"清单与预警黄标提示；医生端可生成版本化健康摘要并导出打印版；家属可查看摘要并回执"已阅"（重复回执幂等）。

### US-14 家属健康 AI 解读（正式功能）

**作为**异地家属，**我希望**在不接触原始病历的前提下，对关联长者的基础健康档案获得一份通俗易懂的 AI 解读，**以便**及时理解老人身体状况并配合照护。

验收要点：

- 仅 family/admin 角色且持有该长者 basic 级查看授权时可发起；未配置模型服务时接口返回 503 且前端按钮置灰（公开开关接口可查询服务是否可用）。
- 出域数据白名单：仅 basic 级四类条目名与内容，自动去除姓名、UUID、房间号等标识；confidential 级内容服务端剔除、永不出库。
- 同一长者每小时最多发起 1 次，超限 429；模型调用失败返回 502 且不留档，成功才写入分析快照（含模型名、提示词版本、发起人）。
- 解读输出固定包含免责声明：仅供参考、不构成诊断，异常情况请咨询医生或线下就医；系统不做医疗诊断的红线不变。
- 历史分析记录可回看，家属只能看到自己关联长者的记录。

## 5. 典型使用场景

### 场景一：早晨用药闭环

08:00 调度器触发提醒 → 数字人主动外呼 → 长者口头确认 → 写入用药事件。若无应答，5 分钟后重试；三次失败后生成工单并通知对应护工。

### 场景二：白天陪伴与娱乐

长者说“我想听越剧” → 规则层或 System One 识别 → 读取本人偏好 → 检索授权曲库 → 平板播放并同步记录。长者说“换一个”时不调用大模型。

### 场景三：复杂信息请求

长者提出需要多个步骤的请求 → 规则层无法处理 → System One 低置信或判定复杂 → CompanionAgent 在工具预算和身份约束下规划调用 → 结果经 TTS 和 3D 形象反馈。

### 场景四：晚间健康采集与家属日报

定时采集健康问答 → Pydantic 结构化输出 → 阈值规则分级 → 正常入库，异常进入 HITL → 次日生成授权摘要并推送家属。

### 场景五：敏感事件

长者说“我胸口疼” → 安全模块优先命中 → 不调主控 Agent → 播放预设安抚话术 → 创建待人工确认事件 → 按确认结果通知护工或医生。

### 场景六：双人间身份不清

设备给出候选住户 → 声纹置信度不足 → 数字人主动询问身份 → 确认失败进入通用模式 → 禁止个人记忆、健康记录和用药信息访问。

### 场景七：方言用药确认

长者用方言回答用药提醒 → ASR 输出原始转写和置信度 → 系统发现否定词或剂量相关语义不清晰 → 数字人用长者能理解的语音复述关键内容并请求确认 → 确认后才进入原用药子图；无法确认时按无明确确认处理，不擅自记为已服药。

### 场景八：累计关怀解锁礼包

家属在 H5 为关联长者签到并发送语音问候 → 服务端校验关联关系和社区日期 → 累计有效签到与关怀行动 → 达到当前规则天数后幂等解锁礼包 → 家属查看领取凭证 → 运营人员线下核验并核销，全程不开放额外个人数据。

### 场景九：家属查看健康档案并发起 AI 解读

管理员在后台为家属配置"基础查看 + 隐私查看"授权 → 家属打开关联长者健康档案弹窗，逐类浏览档案条目（重大疾病对无隐私授权的家属不可见）→ 家属点击"AI 解读" → 服务端校验授权与频控 → 仅 basic 级条目脱敏后出域 → 返回带免责声明的通俗解读并存档 → 家属查看医生健康摘要并回执"已阅"；护工端则只看到同一位长者的基础体征档案，重大疾病记录完全不可见。

| FR-18 | 健康档案分级授权 | 五类纵向档案、basic/confidential 数据分级、范围判定 + 授权 ACL + 分级过滤三层访问控制、写操作审计流水、今日待录入清单、预警提示、医生版本化摘要与家属已阅回执、打印版导出 | P0 |

## 7. 业务边界

MVP 明确不做：

1. 不做医疗诊断，不给出疾病判断或处方建议；异常只记录、提示咨询医生并转人工。
2. 不替代 SOS 紧急呼叫，急救仍由护士站和既有紧急流程负责。
3. 不做高精度 3D 建模、动捕或自研图形学，只使用现成 VRM 和口型驱动。
4. 不做 AI 歌曲生成或演唱。
5. 不依赖商业 Jev API，敏感语音文本不发送到该付费推理服务。
6. 不爬取、不抓取盗版媒体，只使用授权、教学或公有领域资源。
7. 不接支付、采购、门禁等物业系统。
8. 不长期保存完整病历或原始录音；必要临时音频最长 72 小时自动删除。
9. 不做移动端原生 App，不做多租户 SaaS，不做完整多人重叠语音分离。
10. 教学阶段不接真实 HIS，全部使用模拟数据和 mock 接口。
11. 方言能力不通过自动操作网页版对话产品实现，不让外部对话模型绕过项目安全链路自主回答或调用业务工具。
12. 方言 MVP 只验证一种目标方言，不承诺多方言自动识别、混合方言分离或所有方言的识别效果。
13. 签到和礼包不兑换额外健康、记忆、原始对话等隐私权限，不与长者健康指标绑定，不采用连续签到中断清零的惩罚机制。
14. 礼包 MVP 只做教学模拟权益和线下核销，不接支付、采购或真实商品履约。
15. 健康 AI 解读不做医疗诊断、不给药量建议、不判断病情走势；只基于 basic 级脱敏条目输出生活方式层面的通俗提示并附免责声明；confidential 级内容不参与任何出域计算，模型服务不可用时功能整体降级关闭而不是换用不受控通道。

## 10. 验收与发布门禁

1. 功能门禁：用药、健康、身份、权限、敏感事件和降级流程通过场景验收。
2. 安全门禁：三道隔离、注入、越权、脱敏测试全部通过；高风险文件完成人工审查。
3. 性能门禁：延迟、分类准确率、敏感召回率和闭环率达到目标，或明确记录未达标项并拒绝发布。
4. 数据门禁：迁移经过审查；音频删除、声纹加密和记忆隔离可验证。
5. 观测门禁：随机抽取一次对话，可在日志与 Trace 系统串起完整链路。
6. 部署门禁：新环境一键启动、HTTPS 可访问、回滚演练成功。
7. 文档门禁：README、PRD、TDD、ADR、Harness、身份、安全、AI 使用、评测与版本记录一致。
8. 新增能力门禁：方言和家属关怀分别通过 POC-10、POC-11 后才可宣称对应能力完成；未通过时保留普通话/文字或人工线下处理，不虚构效果。

## 12. 与其他文档的关系

- PRD 是需求与验收基线，定义“做什么、为什么做、做到什么程度”。
- TDD 必须逐项实现 PRD 的 FR/NFR/POC，定义“如何做”。
- ADR 记录关键技术选择及其理由，定义“为什么这样做”。
- 需求变化先修改 PRD；技术方案变化先检查 ADR，再修改 TDD；代码与测试必须回链到对应需求编号。
