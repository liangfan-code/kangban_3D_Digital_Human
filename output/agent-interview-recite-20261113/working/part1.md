## 第一章 总纲：Agent 是什么？Agent 详解

### 1.1 Agent 的定义（必背）

Agent 是围绕 LLM 搭起来的**任务系统**——能感知、能规划、能调工具、能看结果再调整。公式：

**Agent = LLM（推理引擎）+ 规划能力 + 工具调用 + 记忆系统 + 反馈闭环**

完整链路：感知（用户输入 + 环境）→ 理解 → 规划 → 执行 → 观测 → 调整 → 完成。它是一个**控制闭环**，不是一次问答。

### 1.2 Agent 与 LLM 的区别

差别不在"聪不聪明"，而在**有没有目标、状态和行动权**：LLM 输出文本就结束；Agent 要对动作的结果负责。

### 1.3 Agent 与 Workflow 的区别

看**决定权放哪**：固定代码管流程是 Workflow；模型决定下一步是 Agent。生产最常见混合方案——外层工作流保证可控，关键节点让 Agent 自主决策。

### 1.4 OODA 决策循环

观察（Observe）→ 判断（Orient）→ 决策（Decide）→ 行动（Act）。第二个 O 是 **Orient（判断）**，不是"定位"。ReAct 是这个循环在单次任务里的落地形态（Thought→Action→Observation）。

### 1.5 生产级架构：六层 + 四件套

六层：入口层 → 编排层（Planner）→ 模型层 → 工具层 → 记忆层 → 缓存层。请求先过网关做鉴权限流与会话路由，Executor 按序调用模型和工具，安全模块审核结果，聚合器输出。

生产四件套：**权限控制、日志追踪、失败重试、人工兜底**（可观测、可回滚、可限轮次）。

记忆层分：短期记忆（任务上下文与执行状态）+ 长期记忆（关系库、KV、事件日志、对象存储与向量索引组合；RAG 是召回利用外部信息的方法，不等于长期记忆）。

### 1.6 四种工作模式

- **ReAct**：思考→行动→观察循环，适合不确定性高的多步推理；
- **Plan-and-Execute**：先列计划再逐步执行，效率高，适合路径相对确定的任务；
- **Multi-Agent**：流水线/辩论/层级结构，分工协作，降低单 Agent 认知负担，代价是协调成本；
- **Reflexion**：执行后自我评估、从失败中反思修正，用推理成本换输出质量。

规划、记忆、反思均为**可选增强**，是否引入取决于任务与成本，不是 Agent 的强制组成。

### 1.7 会话中的 5 类 Message

System（角色规则与约束）、User（用户输入）、Assistant（模型回复或决策）、Tool Call（模型发起的结构化调用，OpenAI 格式里是 assistant 消息的 `tool_calls` 字段，不是独立 role）、Tool Response（工具结果回填，`role="tool"` + `tool_call_id`）。组合成闭环：思考 → 调用 → 观察 → 再思考。

### 1.8 生态分层一图流（防混淆）

- **FC**：模型输出结构化调用意图（协议机制）；
- **MCP**：统一插头，AI 界的 USB-C（工具怎么标准化接入与治理）；
- **Skills**：编排层封装（把多个工具按流程编成能力）；
- **A2A**：Agent ↔ Agent 横向协作协议（区别于 MCP 的纵向接能力）；
- **MQ / Redis / 注册中心 / 网关 / 可观测**：工程底座。

### 1.9 三句话总结全领域

1. 大脑负责决策，代码负责执行——权限永远在服务端，不在模型；
2. 状态管事实、摘要管语境、截断管预算——上下文工程是让模型在对的时机看到对的信息；
3. 可观测、可回滚、可限轮次——生产级 Agent 的底线是失败兜底，不是不失败。

## 第二章 Agent 基础与架构

### 题1｜什么是 Agent？与 LLM 有什么区别？★高频

**a 问题**：什么是 Agent？它和 LLM 有什么区别？

**b 参考答案**：一句话：Agent 是围绕 LLM 搭起来的任务系统——能感知、能规划、能调工具、能看结果再调整；LLM 只是其中的推理引擎。要点：① 公式 Agent = LLM + 规划 + 工具调用 + 记忆 + 反馈闭环；② 链路是"感知→理解→规划→执行→观测→调整"的控制闭环，不是一次问答；③ 区别不在聪明与否，而在有没有目标、状态和行动权——LLM 输出文本就结束，Agent 要对动作结果负责；④ 面试官真正听的是你能否讲清闭环中每一环的失败处理。

**c 可能追问1**：Agent 和 Workflow 有什么区别？

**d 追问参考答案1**：决定权放哪——固定代码管流程是 Workflow，模型决定下一步是 Agent。生产常用混合方案：外层工作流保证可控，关键节点让 Agent 自主决策。

**e 可能追问2**：工具返回了 success=true，但数据库写入失败，任务算成功吗？

**f 追问参考答案2**：以业务最终状态定义成功，不以工具返回值定义。检查持久化结果与必要下游副作用；数据库写入是完成条件时标记"部分完成/待恢复"，保留操作流水，执行安全重试或补偿。验收要查工单是否真创建（tool_call_id 关联业务单号），不是只看回复文字。

**g 设计概念详解**：LLM 是"大脑"，Agent 是"带手脚、有记性、能闭环的完整系统"。工程上把任务目标、可执行工具清单、执行状态与完成判据**显式建模**，结果由业务数据库确认而非模型口头宣告——这就是"模型决策与应用执行"的分界线。

### 题2｜Agent 的完整架构一般包含哪些部分？★高频

**a 问题**：Agent 架构一般包含哪些部分？生产环境还要补什么？

**b 参考答案**：一句话：架构围绕模型决策、状态、工具执行和反馈闭环组织；生产环境重点补权限、日志、失败恢复和人工兜底。要点：① 参考能力划分：大模型推理 / 规划 / 记忆 / 工具调用 / 外部知识检索 / 执行器 / 观测反馈，模块可合并不强制分层；② 六层拆法：入口→编排（Planner）→模型→工具→记忆→缓存，网关先做鉴权限流与会话路由；③ 记忆层分短期（任务上下文与执行状态）与长期（关系库/KV/事件日志/向量索引组合）；④ 生产级补四件套：权限控制、日志追踪、失败重试、人工兜底。

**c 可能追问1**：为什么这样分层？每层边界在哪？

**d 追问参考答案1**：讲职责边界比画框图重要。答法：每层职责单一、失败兜底独立——例如鉴权不该放在模型层（模型不可信），工具校验不该塞进 Prompt。能说出"哪些能力不该放在这一层"是加分点。

**e 可能追问2**：你的架构和别人的有什么不同？

**f 追问参考答案2**：答差异化的取舍——成本、延迟、合规三角（例如我用三级路由换成本、用规则前置换延迟），而不是堆名词。讲述顺序：业务场景→分层理由→每层职责与失败兜底→生产保障（监控、回滚、限流、成本）。

**g 设计概念详解**：分层的本质是**关注点分离**：决策（模型）、状态（记忆）、行动（工具）、边界（网关/安全）各自独立演进、独立失败兜底。生产四件套对应"可观测（日志追踪）、可回滚（失败重试+人工兜底）、可限权（权限控制）"。

### 题3｜Agent 的自主决策流程是如何工作的？★

**a 问题**：Agent 的自主决策流程是怎样的？

**b 参考答案**：一句话：感知 → 规划 → 记忆 → 执行，本质是 OODA 循环：观察→判断→决策→行动。要点：① 感知不止看用户输入，还观察环境（读文件、搜网页、监听数据库），把原始信息转成模型可读的环境描述；② 规划做任务拆解，用 CoT 或 ReAct 让模型自问自答"我在哪、要做什么、第一步做什么"；③ 记忆分短期（当前对话与任务状态）与长期（跨任务可复用信息），工程细节是滑动摘要防 Token 爆炸；④ 执行是模型的手脚，真正落地动作。

**c 可能追问1**：OODA 和 ReAct 什么关系？

**d 追问参考答案1**：ReAct 是决策循环在单次任务里的落地形态（Thought→Action→Observation），OODA 是更高层的认知模型。注意纠偏：OODA 第二个 O 是 Orient（判断/定势），不是"定位"，面试写"观察-判断-决策-行动"最稳。

**e 可能追问2**：RAG 和长期记忆是一回事吗？

**f 追问参考答案2**：不是。RAG 是一种召回与利用外部信息的方法；长期记忆是跨任务保存可复用信息的机制。长期记忆可用关系库、KV、事件日志、向量索引组合实现，向量召回只是其中一路。

**g 设计概念详解**：OODA 源自军事决策模型，价值在于强调"判断（Orient）"——结合经验与情境理解态势后再决策。Agent 借用它说明：决策质量取决于观察的完整性和判断的准确性，工程上分别对应感知层的信息治理和上下文构造。

### 题4｜如何让 Agent 长任务不跑偏、不摆烂？★

**a 问题**：长任务执行中 Agent 容易跑偏、摆烂，怎么治理？

**b 参考答案**：一句话：靠机制不靠模型自觉——规划层、状态跟踪层、目标对齐层三层能力 + 执行管控四件套。要点：① 根因：Agent 只有执行能力、没有任务管控能力，长任务缺目标锚定与状态跟踪就会跑偏；② 三层能力：任务规划层（大目标拆步骤）→ 状态跟踪层（每步输入/输出/进度结构化记录）→ 目标对齐层（每步执行前锚定原始目标）；③ 四件套：目标锚定（持久化任务状态、每轮对齐校验）、步骤校验（查重复/越界/擅自加需求）、关键节点自省（子任务完成或失败时才反思，不是每轮）、进度熔断（最大步数/工具调用数/时长）；④ 断点续跑五步：checkpoint 持久化→幂等键→状态恢复（读最新快照）→进度汇报→人工交接。

**c 可能追问1**：批量任务跑到第 8 个文件时容器退出，怎么恢复？

**d 追问参考答案1**：每阶段持久化 checkpoint、已完成文件哈希与任务状态；恢复时核对产物，未完成步骤重跑，外部写入用幂等键。验证：模拟第 8 个文件完成后宕机，重启只处理未完成文件，核验产物数量与总清单一致。

**e 可能追问2**：已写入外部系统但 checkpoint 未提交，重启后怎么避免重复执行？

**f 追问参考答案2**：为副作用操作预生成稳定的业务操作 ID，在持久存储记录发起与完成状态。恢复时先按 ID 查询外部最终结果：已成功则补记 checkpoint，未执行才重试，状态不明则暂停核对。不能仅靠 checkpoint 保证恰好执行一次（exactly-once）。

**g 设计概念详解**："失控三层"对应关系：检测偏离（步骤校验）→ 降级降权（进度熔断）→ 人工接管（人工交接）。依赖校验保证有前置条件的步骤不提前跑；动态重规划允许失败后改后续步骤。这比"加个 max_steps"高一档。

### 题5｜Agent 支持并行执行多个任务吗？

**a 问题**：Agent 能并行执行多个任务吗？判断依据是什么？

**b 参考答案**：一句话：可以串行也可以并行，取决于任务依赖、执行框架、状态隔离与工具副作用。要点：① 单 Agent 多任务并行：调度器把每个任务的上下文、记忆、工具会话隔离，任务队列+线程池分发到协程/线程；② 判据：无先后依赖且并发安全可并行；有依赖保顺序；共享资源写入要锁、事务、乐观并发或幂等；③ 企业级平台里并行的价值在吞吐与资源利用率，代价是隔离成本与可观测复杂度。

**c 可能追问1**：什么时候并行反而更慢？

**d 追问参考答案1**：任务过小、下游限流、锁竞争或合并开销大时更慢。按下游 QPS、并发连接数及 Token/速率配额设独立信号量和限速器，监控 P95/P99、429 与排队时间，动态调整并发上限。

**e 可能追问2**：同时查询三个独立数据源，怎么设计？

**f 追问参考答案2**：异步调度并发查询，分别设超时和并发上限，按 task_id 隔离结果，合并阶段处理部分失败。验证：结果不串会话、总耗时接近最慢分支、下游并发不超配额。

**g 设计概念详解**：并行度设计本质是**隔离与配额**问题：任务级隔离（上下文/记忆/会话互不污染）+ 资源级配额（下游容量保护）。一次模型响应也可以请求多个并行工具调用（parallel tool calls）。

### 题6｜多轮对话 Agent 怎么解决状态爆炸、上下文溢出？★

**a 问题**：多轮对话中状态爆炸、上下文溢出怎么办？

**b 参考答案**：一句话：规范状态结构 + 智能截断 + 分层摘要三件套，原则是"状态管事实、摘要管语境、截断管预算"。要点：① 规范状态结构：固定 schema（TypedDict/Pydantic）定义目标、槽位、关键实体、已执行步骤，只更新字段，不把聊天记录当状态；② 智能截断按语义优先级裁：系统提示与约束 > 当前任务目标 > 最近 2–3 轮 > 工具结果配对 > 早期对话，按 Token 预算裁不按字符数硬切；③ 分层摘要：近期原文、中期滚动摘要、远期"事件+指针"可回源；④ 执行顺序：先抽事实进状态→再压语境→最后卡预算；⑤ 压缩后校验：让模型复述"当前目标/已完成/下一步"，复述不出说明压过头。

**c 可能追问1**：用户对话 100 轮后仍要引用第一轮确定的合同编号，怎么保证不丢？

**d 追问参考答案1**：合同号与约束写入结构化状态；保留关键原文来源指针，滚动摘要只处理叙事；按 Token 预算注入。验证：长对话中持续改写合同信息，第一轮编号不被摘要覆盖，最新纠正覆盖旧状态，引用能回源。

**e 可能追问2**：摘要中合同号被改写了，怎么检测并修正？

**f 追问参考答案2**：合同号等关键标识先抽取为受校验的结构化字段并与原文 span 绑定，摘要只能引用不可自行改写；压缩后做精确字符串/格式校验，失败时从原始记录恢复并重新生成摘要。

**g 设计概念详解**：核心思想是**事实与叙事分离**：事实（编号、约束、槽位）走结构化状态、精确可校验；叙事（过程、语气）走摘要、允许有损。压缩应做成独立节点，输入输出可测。

### 题7｜生产级 Agent 系统架构怎么讲才加分？★高频

**a 问题**：面试让你讲生产级 Agent 架构，怎么讲？

**b 参考答案**：一句话：别一上来画框图，先讲切分逻辑——为什么这样分层、每层职责边界是什么，再补可观测、可回滚、可限轮次。要点：① 六层结构（入口/编排/模型/工具/记忆/缓存）+ 网关鉴权限流 + Planner 拆解 + Executor 执行 + 安全审核 + 聚合器输出；② 讲述顺序：业务场景→分层理由→每层职责与失败兜底→生产保障（监控、回滚、限流、成本）；③ 加分点：说出"哪些能力不该放在这一层"（如鉴权不放模型层）。

**c 可能追问1**：哪个环节可以重试，哪个必须先查最终状态？

**d 追问参考答案1**：纯读取、可幂等的计算、明确未提交的操作可在预算内重试；付款、发信、创建工单等有副作用的请求遇超时或 5xx，必须先用业务 ID 查询最终状态；无法确认进入待核对队列，不能盲重试。

**e 可能追问2**：客服系统要支持审批、支付查询和知识库回答，架构怎么设计？

**f 追问参考答案2**：画入口鉴权、编排状态机、模型网关、工具授权、检索 ACL、持久存储和 tracing，明确每层失败边界。验证：让知识库、审批、支付各失败一次，验证隔离、审计和人工接管链路，确保审批未通过时不能执行写操作。

**g 设计概念详解**：讲架构的区分度在**取舍叙事**而非组件清单：为什么用这个分层（团队规模/迭代速度）、放弃了什么（延迟换可控性还是成本换质量）、失败怎么兜底。架构图的每一根线都应该对应一个失败分支。

### 题8｜Agent 有哪些常见工作模式？★

**a 问题**：Agent 的常见工作模式有哪些？怎么选？

**b 参考答案**：一句话：ReAct、Plan-and-Execute、Multi-Agent、Reflexion 四种，按任务的确定性与并发收益选。要点：① ReAct 思考→行动→观察，适合不确定性高的多步推理；② Plan-and-Execute 先列计划再执行，效率高，适合路径相对确定的任务；③ Multi-Agent 流水线/辩论/层级结构，分工降低单 Agent 认知负担，代价是协调成本；④ Reflexion 执行后自我评估修正，用推理成本换输出质量。

**c 可能追问1**：ReAct 和 Plan-and-Execute 怎么选？

**d 追问参考答案1**：选"任务可预见性"：可预见性强用 Plan（先列计划效率高），边做边看用 ReAct（每步根据观察纠偏）。

**e 可能追问2**：规划、记忆、反思是不是 Agent 必备组件？

**f 追问参考答案2**：不是。它们都是可选增强能力，是否引入取决于任务复杂度与成本预算；简单任务一个 ReAct 循环加工具就够了，硬堆组件只会增加失败面。

**g 设计概念详解**：模式选择本质是**自主性配比**问题：任务越确定，越应该把决策从模型移到代码（降本提速）；任务越开放，越需要模型临场决策（ReAct/Multi-Agent）。

### 题9｜单轮 Agent 和多轮 Agent 的设计差异是什么？

**a 问题**：单轮和多轮 Agent 设计上有什么差异？

**b 参考答案**：一句话：单轮一般不需要跨轮会话状态（但复杂单轮任务仍需执行状态）；多轮额外需要会话状态与上下文管理，不能无条件每轮传全量历史。要点：① 单轮：无需跨请求对话状态，多步任务仍保存计划、工具调用和检查点，简单任务易水平扩展；② 多轮：需要会话 ID + 状态对象 + 记忆持久化；全量历史导致 Token 成本随轮数爆炸、长上下文稀释注意力产生"中间遗忘"；③ 上下文超限三选：滑动窗口（简单但丢早期）、摘要压缩（保全局但有损）、结构化状态（最省 Token 但要维护 schema）；生产常用**摘要+结构化状态**组合：近几轮原文 + 早历史摘要 + 关键事实结构化。

**c 可能追问1**：用户中途纠正、打断、切换话题，分别怎么处理？

**d 追问参考答案1**：纠正→更新状态字段（不是追加一轮对话）；打断→终止当前动作（工具要支持取消）；切换话题→重置当前任务上下文，长期记忆保留。

**e 可能追问2**：哪些信息必须保留原文？

**f 追问参考答案2**：约束条件、工具调用与返回的配对、证据链（引用来源）——这三类被摘要掉就会出事故，是上下文裁剪的红线。

**g 设计概念详解**："中间遗忘"（lost in the middle）：长上下文里模型对中段信息注意力下降，所以关键信息要么放开头（系统提示）要么结构化进状态，不能赌"塞进窗口就记得"。

### 题10｜Agent 会话中的 5 类 Message 是什么？★

**a 问题**：Agent 会话中有哪几类 Message？协议上怎么映射？

**b 参考答案**：一句话：按语义角色分五类——System、User、Assistant、Tool Call、Tool Response；落到主流协议上是 system / user / assistant / tool 四种 role。要点：① System 初始化角色规则与约束；② User 承载用户输入；③ Assistant 是模型回复或决策；④ Tool Call 是模型主动发起的结构化调用（OpenAI 格式里是 assistant 消息的 tool_calls 字段，不是独立 role）；⑤ Tool Response 是工具结果回填（role="tool" + tool_call_id）。组合成闭环：思考→调用→观察→再思考。

**c 可能追问1**：为什么工具结果要单独成一条消息？

**d 追问参考答案1**：为了保持调用与结果的配对（tool_call_id 对应），压缩上下文时不能拆散，否则模型无法判断哪次调用产生了哪个结果，二次推理会错乱。

**e 可能追问2**：五类消息在压缩上下文时的优先级？

**f 追问参考答案2**：System 与约束最高（不可裁）；当前任务目标其次；最近 2–3 轮对话保原文；工具调用与返回按配对整体处理（可转为结构化状态）；早期闲聊最先裁。

**g 设计概念详解**：消息模型的本质是给**对话赋予可执行语义**：assistant 从"说话者"变成"决策者"，tool role 把外部世界的结果引入推理链。理解了这一层，就理解了为什么 Agent 对话不是普通聊天记录。

### 题11｜多模态 Agent 怎么做？

**a 问题**：多模态 Agent 怎么设计？有哪些硬考点？

**b 参考答案**：一句话：多模态就是给 Agent 装上眼睛和耳朵——感知（VLM）、规划（大脑）、工具（手脚）、记忆（笔记本）四模块，外加一条降级链路。要点：① 链路：输入（文本+图像/音频）→ 感知模块 → 任务规划 → 工具调用 → 答案；② 落地硬考点：按通道拆分预处理、图片理解去噪、时序对齐（音视频）、图文冲突消解、输入治理；③ Token 治理：图像视频的 Token 成本因模型/分辨率/帧采样差异很大，原始素材放外部存储按需回取，进模型的只放"摘要+引用 ID+少量原文"；④ 降级链路：多模态失败降级纯文本，别让整条链路挂死；⑤ 语音 Agent：STT→Agent→TTS 三件套，难点在打断检测、流式对话、端到端延迟。

**c 可能追问1**：图片密集文档用 OCR 还是多模态模型？

**d 追问参考答案1**：文本密集、版式简单的图像，比较 OCR+结构化与多模态模型的质量、成本和延迟再选；复杂图表和视觉关系更适合多模态或混合解析（OCR 提文字 + VLM 理解版面关系）。

**e 可能追问2**：多模态失败怎么兜底？

**f 追问参考答案2**：降级链路——VLM 失败或超时降级纯文本链路（OCR 或原始描述）；语音失败降级文字通道。降级要可见（明确告知用户能力受限），不能静默给错误结果。

**g 设计概念详解**：多模态的成本陷阱在**上下文膨胀**：一张图几百到几千 Token，视频按帧累积。原则是"决策摘要与原始素材分开存"——模型消费压缩表示，审计和回源用原始素材，两者用引用 ID 连接。
