## 第三章 Agent 设计与项目方法论

### 题12｜如何从 0 到 1 设计一个 Agent？★高频

**a 问题**：让你从 0 到 1 设计一个 Agent，怎么做？

**b 参考答案**：一句话：六步法——定问题、拆能力、分层架构、抠细节、做 MVP、上线闭环。要点：① 明确核心问题：锁定具体场景（客服工单、周报生成），不做全能助手；② 拆解核心能力：按感知、决策、执行、闭环拆，先判断输入是纯文本还是多模态；③ 分层架构：模型层（大脑）→工具层（外部交互）→记忆层（短期任务状态/长期多类型存储）→编排层（任务流程）；④ 打磨细节：固定任务用 Workflow、动态任务用 ReAct；工具入参出参描述标准化；容错（重试+人工介入）；⑤ MVP 用真实数据跑通，盯任务完成率、平均轮次、工具调用准确率、用户满意度；⑥ 上线闭环：收集失败案例与反馈，针对性调 Prompt、加工具、加判断逻辑。

**c 可能追问1**：规划能力怎么补强？

**d 追问参考答案1**：六策略：任务拆解（DAG/依赖）、计划校验与重计划、里程碑检查点、目标对齐、风险预判、失败回退。

**e 可能追问2**：哪一步最容易失败？

**f 追问参考答案2**：工具语义设计与失败恢复——工具描述写得含糊，模型就选错工具；失败路径没设计，一次超时就让任务挂死。要能给出自己项目的具体案例。

**g 设计概念详解**：六步法的内在逻辑是"收敛"：先把无限需求收敛到一个场景（①），再把场景收敛为能力集合（②③④），最后用指标收敛质量（⑤⑥）。反例是"先选框架再找问题"。

### 题13｜Workflow 和 Agent 怎么选？★高频

**a 问题**：架构设计中 Workflow 和 Agent 怎么选？

**b 参考答案**：一句话：看每一步的"决定权"放哪——路径固定的写代码（Workflow），需要临场判断的交给模型（Agent），中间地带用确定性骨架管流程。要点：① 简单、固定、重复任务→Workflow：确定性高、成本低、可测试；② 需要灵活应变、动态调整的复杂任务→Agent 循环（ReAct），根据实时反馈调整策略；③ 本质是确定性 vs 自主性的配比：核心数据写入用固定代码，意图理解交给模型，再逐步开放自主性；④ 生产最常见混合方案：外层工作流保证可控，关键节点让 Agent 自主决策。

**c 可能追问1**：报销流程既有固定审批规则，也有自然语言票据解释，怎么设计？

**d 追问参考答案1**：审批门槛、金额校验写成确定性 Workflow；模型处理票据理解和例外说明；高风险节点人工确认。验证：故意给不符合规则的票据，规则节点必须拒绝，模型只能解释原因，不能改变金额上限和审批状态。

**e 可能追问2**：如果模型建议跳过财务审批，运行时怎么阻止？

**f 追问参考答案2**：把审批约束编码在工作流状态机和服务端鉴权里，不是只写在 Prompt。付款节点必须校验有效审批记录、审批人权限及金额范围；条件不满足直接拒绝执行并记录审计事件。

**g 设计概念详解**：错误答法是"越复杂越该用 Agent"；正确的是"先问失败代价，再决定放权多少"。放权矩阵：失败代价低、路径开放→Agent；失败代价高、路径固定→Workflow；中间→混合（Agent 提建议，Workflow 卡关口）。

### 题14｜单智能体 vs 多智能体，什么场景怎么选？★高频

**a 问题**：单 Agent 和多 Agent 怎么选？

**b 参考答案**：一句话：不看任务复不复杂，看两件事——并发收益和上下文需求；线性任务优先单 Agent。要点：① 错误答法："任务越复杂越适合多 Agent"是过度设计；② 线性任务单 Agent 够：多 Agent 带来延迟爆炸（每节点秒级）、Token 成倍消耗、bug 难定位；③ 多 Agent 杀手锏：任务天然可并行、需要专业分工、需要互相检验；④ 案例：智能客服（线性，单 Agent）vs 代码安全审计（多 Agent 分工+对抗）；⑤ 选型四问：能不能拆、领域是否隔离、有没有并发收益、上下文是否装不下。

**c 可能追问1**：多 Agent 数量增加但成功率下降，怎么定位协调开销？

**d 追问参考答案1**：按 trace 记录，比较模型调用次数、上下文重复量、消息往返时延、交接失败率、冲突率及任务成功率；对照单 Agent 基线做消融——逐步撤掉 Reviewer/协作者，定位收益小于协调成本的环节。

**e 可能追问2**：多 Agent 的成本项有哪些？

**f 追问参考答案2**：协调成本（仲裁/通信）、重复上下文（每个 Agent 都要装一份背景）、错误放大（一个节点幻觉沿链路传播）。能说出成本项比只讲好处可信。

**g 设计概念详解**：多 Agent 收益本质来自**上下文隔离**（每个 Agent 只装自己领域的上下文，减少污染与稀释）与**并行探索**（多方案同时验证），不是"人多力量大"。SWE-bench 类任务上多 Agent 的收益主要来自并行探索+交叉验证。

### 题15｜什么样的 Agent 项目才真正有含金量？★

**a 问题**：Agent 项目做到什么程度才算有含金量？

**b 参考答案**：一句话：真实问题 + 完整后端 + Agent 核心能力 + 上下文工程 + 可观测 + 人机协同，六条标准。要点：① 解决真实问题：明确业务场景、有用户需求、完整流程、可评估效果，"你一句它一句"只是聊天机器人；② 完整后端工程：API、数据库、权限、日志、异常处理、并发——只有 Prompt+调用链就是 Demo；③ 体现 Agent 核心能力：任务规划、拆解、工具调用、失败恢复、结果验证，别为炫技硬堆 Multi-Agent；④ 上下文工程：让模型在正确时机看到正确信息；⑤ 可观测性：调用成功率、失败步骤定位、响应速度、单次成本、结果准确率；⑥ 人机协同：资金、隐私等高危操作保留人工确认关卡。

**c 可能追问1**：怎么证明你的项目有含金量？

**d 追问参考答案1**：每条标准都落到"你做了什么改动+指标变化"——例如失败恢复上线后任务完成率从 X% 提到 Y%，否则就是背清单。

**e 可能追问2**：上下文工程具体指什么？

**f 追问参考答案2**：管理模型每一轮看到的信息——任务状态、用户偏好、企业知识、工具返回的分发与注入时机。目标是对的信息在对的时机出现，而不是把窗口塞满。

**g 设计概念详解**：含金量的试金石是"为什么"：Demo 级只有"做了什么"，项目级答得出"为什么这么做"，生产级还能答"失败了怎么办"。

### 题16｜项目做到什么程度才敢写进简历？

**a 问题**：Agent 项目做到什么程度才敢写进简历？

**b 参考答案**：一句话：能跑只是 Demo，能回答"为什么这么设计"才是项目，能上线稳定运行才是生产级。要点：① 三级判断：Demo（能跑通）→ 项目（有取舍、有评测）→ 生产（稳定、可观测、可回滚）；② 项目级要答得出：切片策略、Embedding 选型、召回失败怎么办、RAG 与微调的取舍、成本与延迟的平衡，并有像样的评测集；③ 生产级：API/数据库/权限/日志/并发齐全，有灰度与回滚、人工兜底、成本核算；④ 简历写法：问题+方案+结果（基线、样本量、口径），一个项目 3–5 行，留 1–2 个可深挖的钩子；反面："基于 XX 框架实现了智能问答"没有取舍没有数字，等于没写。

**c 可能追问1**：你有失败案例吗？

**d 追问参考答案1**：准备"一个失败案例+怎么定位+改完指标变化"，再准备"如果重做会怎么改"——这两问最能看出是不是真做过。

**e 可能追问2**：简历上的数字被问基线是什么、怎么测的、样本量多大，能答上吗？

**f 追问参考答案2**：每个数字都要能回答三件事：基线是什么、怎么测的、样本量多大；答不上就别写这个数字。

**g 设计概念详解**：简历的叙事结构是"钩子"：正文 3–5 行给结论，把深度藏在可追问的细节里（评测集怎么建、幂等怎么做），面试官往哪挖你都有料。

### 题17｜Harness 是什么？Agent 项目为什么总落地难？★

**a 问题**：Harness 是什么？为什么 Agent 项目总落地难？

**b 参考答案**：一句话：Harness 是模型之外的工程外壳（Agent = Model + Harness）——统管提示词、工具、记忆、沙箱、可观测与反馈；落地难就难在这层外壳没搭好。要点：① 两种含义要分清：测试夹具（为 Agent 构造可控测试环境：Mock 工具返回、注入异常、验证调用序列）；运行时/驾驭层（沙箱隔离、任务调度、可观测、治理审批）；② 生产级要素：安全隔离（容器沙箱、文件系统只读、出网白名单、资源限额）、高并发（任务队列、限流、异步）、可观测（调用链、成本计量）、治理（权限、审批、回滚）；③ 落地难三根因：不稳定（输出不可控）、不可观测（出问题定位不了）、不可治理（权限/安全/成本失控）。

**c 可能追问1**：Harness 与 Prompt 工程、上下文工程的分工？

**d 追问参考答案1**：Prompt 管"怎么问"，上下文管"读什么"，Harness 管"怎么兜底"——三层各管一段，别混着答。

**e 可能追问2**：Mock 不准、权限过紧业务跑不通，怎么办？

**f 追问参考答案2**：Mock 要基于真实调用 trace 抽样回放，不能拍脑袋造返回；权限先按最小可用放开核心链路，再逐工具收紧，用调用成功率回归验证收紧没有打断业务。

**g 设计概念详解**：把"模型能力"和"工程能力"分离后才能分别优化：模型不行换模型（Harness 不动），工程不行改 Harness（Prompt 不动）。落地难的企业往往只有前者没有后者。

## 第四章 工具调用与 Function Calling

### 题18｜Agent 到底怎么调工具？★高频

**a 问题**：Agent 调用工具的完整流程是怎样的？

**b 参考答案**：一句话：本质是结构化——模型根据工具定义生成结构化调用请求（工具名+参数），应用或工具运行时解析后完成参数校验、权限校验与实际执行，再把结果返回模型继续处理。要点：① 完整流程：问题发过去→模型判断要调工具→生成结构化调用（函数名+参数；不必是 JSON，只需约定好的结构化信息由配套 tool parser 解析）→框架解析执行→结果回填上下文→模型二次推理给答案；② 工具注册：名称、说明、参数规则（JSON Schema）；模型只负责决策，执行权在应用与服务侧；③ MCP 场景多一步协议转换：应用把调用请求转成 MCP 调用格式，Server 执行后返回。点题句："大脑负责决策，代码负责执行"。

**c 可能追问1**：模型填了不存在的 order_id，在哪一层阻止？

**d 追问参考答案1**：先做 Schema 与格式校验，再由业务服务按租户权限查询 order_id 是否存在且属于当前用户。模型猜测的 ID 不可信；校验失败返回可修复错误或向用户确认，禁止直接进有副作用的工具。

**e 可能追问2**：用户要求查订单并发起退款，怎么落地？

**f 追问参考答案2**：工具 schema 约束 order_id 与退款原因；模型只产调用意图，服务端鉴权、校验并执行，返回可关联的 tool_call_id。验证：模型填错订单号时执行层拒绝退款；工具参数校验、用户确认、订单所有权与调用回执形成闭环。

**g 设计概念详解**：FC 的安全模型是"模型不可信"：模型输出只是意图（可能幻觉、可能被注入），一切校验（格式、语义、权限、幂等）都在执行层。这也是为什么"权限放后端不放模型"是铁律。

### 题19｜除了标准 Function Calling，还有什么调用姿势？

**a 问题**：除了原生 FC，还有哪些工具调用方式？

**b 参考答案**：一句话：除了原生 Function Calling，还可采用文本动作协议或结构化输出，由应用解析执行；ReAct、Plan-and-Execute 属于可搭配使用的编排模式，不是另一种底层调用协议。要点：① 提示词约定调用：模型生成文本动作标签或 JSON 调用意图，应用侧解析、校验、执行；可用于 ReAct 但不等于 ReAct 必须文本解析；② Plan-and-Execute 先规划再执行，每步既能调原生 FC，也能调 MCP 或传统 API；③ 比较时要区分"编排策略"和"调用表达/传输机制"两个层次。

**c 可能追问1**：JSON mode 和结构化输出是一回事吗？

**d 追问参考答案1**：不是。JSON mode 只保证特定格式约束（合法 JSON），结构化输出还包括严格 Schema 校验；语法合法不代表字段语义正确，仍需应用侧校验。

**e 可能追问2**：模型没有原生 FC，怎么用工具？

**f 追问参考答案2**：用提示模板把工具描述注入上下文，模型生成结构化文本调用，应用端解析、参数校验、授权后执行——安全性依赖 Host 的校验与权限控制，而非模型是否原生支持 FC。

**g 设计概念详解**：调用方式分两层看——表达层（原生字段 vs 文本约定）与传输层（API 直连 vs MCP 协议）。ReAct/Plan-Execute 是更上层的编排策略，可以搭任意的表达与传输方式。

### 题20｜怎么保证 Agent 工具调用的可靠性？★高频

**a 问题**：工具调用怎么保证可靠？

**b 参考答案**：一句话：四层工程架构——结构化定义、推理策略、执行护栏、自愈修复。要点：① 结构化定义层：JSON 强类型约束（类型/非空/枚举定死），工具描述像写 Prompt 一样讲清不同场景该调哪个工具；② 推理策略层：用任务规划或独立校验节点处理复杂决策，结合 few-shot 正反示例与工具子集检索减少误选；③ 执行护栏层：绝不直接执行模型输出——代码侧校验参数格式，高风险操作（转账/删库）必须人工确认；④ 自愈修复层：脱敏、结构化的可修复错误信息回传模型重新生成参数，调用完成后校验结果是否符合预期，不符则重新规划。公式：可靠性 = 高质量结构化定义 × 严格代码执行约束 × 闭环反思重试机制。

**c 可能追问1**：误调用怎么防？

**d 追问参考答案1**：工具白名单 + 参数语义校验 + 幂等键 + 可回滚/补偿。白名单按会话/租户授权收敛；语义校验查参数是否在合理业务范围。

**e 可能追问2**：接口 500 但实际退款成功了，怎么避免二次退款？

**f 追问参考答案2**：退款请求使用服务端生成的稳定幂等键，建立唯一业务流水；收到 500 后先按流水号查询退款最终状态：已成功只回填结果，明确失败且可重试才重发，状态未知挂起对账。超时后让 Agent 重复调用时，同一业务退款键只能有一次有效退款。

**g 设计概念详解**：四层分别对抗四类失败：定义层对抗误选（选错工具）、推理层对抗歧义（参数拿不准）、护栏层对抗幻觉参数（乱填 ID）、自愈层对抗瞬时故障（超时/限流）。幂等是副作用安全的最后防线。

### 题21｜工具调用失败时，该报错还是重试？★高频

**a 问题**：工具调用失败，报错还是重试？

**b 参考答案**：一句话：先分类再处理——参数错让模型改参重调；目标不存在换目标或终止；临时错误退避重试；条件不满足补条件或改路径。要点：① 参数错误：脱敏的结构化错误信息回传模型，修正参数并通过校验后重调；② 目标不存在：换目标或终止，不盲目重试（重试也不会出现）；③ 临时错误（网络/限流/超时）：判断接口幂等性与请求最终状态；确认可安全重试后，带抖动的指数退避 + 最大次数 + 时间预算。超时不等于调用未生效；④ 条件不满足：补条件或改路径，必要时转人工；⑤ 失败信息进持久事件：只存在几十秒的报错进不了对话历史，Agent 会反复犯同样的错——把失败回执写入持久记录（含纠错与防重复调用标记）；⑥ 三层兜底：执行前任务拆解→执行中护栏（超时熔断、重试退避）→执行后评估（错误复盘进评测集）。

**c 可能追问1**：支付 API 超时但无法判断是否扣款，怎么办？

**d 追问参考答案1**：按参数错误、永久错误、限流与结果未知分类；结果未知时先查单，对可重试接口用抖动退避和总预算。验证：模拟请求已生效但 HTTP 超时——先查业务单状态再决定是否重试，避免把超时当失败导致重复扣款。

**e 可能追问2**：重试发生在不同 worker 上，幂等键怎么保持一致？

**f 追问参考答案2**：幂等键由业务请求 ID 与操作类型等稳定字段生成，写入数据库并随任务消息传递，不能由每个 worker 临时随机生成；通过唯一约束/原子插入登记操作，跨 worker 重试沿用同一键。

**g 设计概念详解**：失败分类学的关键是两个正交维度：**可重试性**（临时 vs 永久）与**结果确定性**（已知失败 vs 结果未知）。超时是结果未知——必须先查终态；参数错是永久但可修复；限流是临时但要退避。MCP 场景五件套：参数校验、权限校验、超时重试、错误分类、人工可读提示。

### 题22｜工具调用该串行还是并行？★

**a 问题**：工具调用什么时候串行、什么时候并行？

**b 参考答案**：一句话：看两件事——数据有没有依赖、操作有没有外部副作用；无先后依赖且满足并发安全时可并行；存在因果依赖时保证顺序；共享资源写入需并发控制（不等于所有写操作都必须串行）。要点：① 无依赖（查订单物流+查店铺售后规则）→并行压缩耗时；② 有因果（先核实退款资格→再调支付退款）→必须保先后顺序；不同订单且无共享约束的写操作可并行；③ 盲目并行的问题：共享状态并发修改冲突、部分失败难合并（缺关键信息时禁止执行，不能交给模型凭感觉）；④ 并行可能压满下游→限制同时执行工具数；写操作重试要幂等（同一业务标识防重复退款）；⑤ 部分失败：先落已成功步骤结果，失败的按分类重试；无法补齐时降级或转人工，不能"带病继续"。

**c 可能追问1**：并行工具调用怎么控制并发？

**d 追问参考答案1**：信号量/线程池限流 + 超时 + 部分失败补偿；按下游配额设并发上限，监控 429 与排队时间。

**e 可能追问2**：乐观锁冲突后，自动重试还是交给业务重新确认？

**f 追问参考答案2**：先重读最新版本，判断冲突是否可自动合并。计数器等可交换、可重算操作可限次重试；库存、金额、权限或用户决策已变化时，重新验证业务前提，必要时让用户确认。反例边界：对同一账户余额的并发修改需事务/锁/版本控制。

**g 设计概念详解**：判据本质是**因果序与互斥集**：同一因果链上的操作必须串行；不同互斥集（不同订单、不同资源分区）的操作可并行。并发控制手段按强度排：事务/锁 > 乐观锁版本号 > 幂等键兜底。

### 题23｜ReAct 模式的原理和缺点是什么？★高频

**a 问题**：ReAct 模式的原理是什么？有什么缺点？

**b 参考答案**：一句话：让模型交替"想一步、做一步、看结果"，用观察纠偏；缺点是链路长、成本高、容易循环。要点：① 原理：Thought→Action→Observation 循环，模型根据上一步观察决定下一步调什么工具；② 为什么能纠错：纯 CoT 是"闭卷考试"，模型看不到外部世界，复杂问题容易编；ReAct 把每步观察喂回推理（HotpotQA、ALFWorld 有论文数据支撑）；③ 停止符（stop sequence）：设在 Observation: 之前——模型写完 Thought/Action 停下，执行权交回框架，由框架真实调用工具后回填 Observation，防止模型自编假观察。注意这是 Prompt-based ReAct 的做法，用原生 FC 时由协议保证，不需要文本停止符；④ 缺点：链路长、成本高、容易循环，容易在错误观察上继续推理。

**c 可能追问1**：怎么防 ReAct 死循环？

**d 追问参考答案1**：工程防线四件套：max iterations、重复动作检测、Reflexion 失败反思写回记忆、LangGraph 显式状态机兜底。加上 few-shot 约束格式。

**e 可能追问2**：ReAct 和 Plan-and-Execute 怎么选？

**f 追问参考答案2**：按任务可预见性——可预见性强用 Plan（先列计划、效率高），边做边看用 ReAct（每步用观察纠偏）。

**g 设计概念详解**：ReAct 的本质是把**外部世界的反馈引入推理链**，把"闭卷"变"开卷"。停止符机制是执行权的分界：框架通过停止符拿回控制权，保证 Observation 是真实工具结果而非模型想象——这是"模型决策、代码执行"在文本协议上的体现。

### 题24｜多模型支持架构怎么设计（模型网关）？★

**a 问题**：系统要接入多家模型，架构怎么设计？

**b 参考答案**：一句话：做一层模型网关——上层只依赖统一接口，底层用 Adapter 适配各厂商，中间用 Router 按租户/场景/成本/延迟路由。要点：① 统一接口：chat / stream chat / embedding，Agent 不直接依赖某厂商 SDK；② Adapter 适配 GPT/Claude/Gemini/DeepSeek 差异（消息格式、工具调用格式、流式协议）；③ Router 策略：简单分类用便宜模型，复杂推理用强模型，失败降级或重试，线上记录效果数据；④ 多租户热更新：配置化不写死，租户配置隔离、请求级配置快照、版本化切换。典型组件：LiteLLM、OneAPI、OpenRouter。

**c 可能追问1**：网关的隐藏价值是什么？

**d 追问参考答案1**：可观测与成本归因——按租户/场景统计 Token 与失败率，才能做容量规划；否则换模型只是换 API 地址，没有数据支撑。

**e 可能追问2**：配置热切换怎么避免读到半套配置？

**f 追问参考答案2**：配置版本化 + 请求级快照——请求开始时固化一份配置版本，整个请求期间用同一版本；切换在新版本全量生效后进行，灰度按租户比例放量。

**g 设计概念详解**：网关是经典防腐层（Anti-Corruption Layer）在 LLM 场景的应用：隔离厂商协议差异、统一鉴权与计量、给路由与降级一个插拔点。没有网关，换一次模型=全工程改造。

### 题25｜后端 Agent 多租户并发调用怎么做隔离？★

**a 问题**：多租户场景怎么隔离？

**b 参考答案**：一句话：数据、配置、资源三层隔离，缺一层就会串台或被打爆；再用租户 ID 贯穿全链路做可运维。要点：① 数据隔离：会话/记忆/知识库按 tenant_id 分区；向量库用独立 collection 或 metadata 强过滤；关系库用行级权限（RLS）；② 配置隔离：模型、Prompt、工具白名单按租户配置，配置版本化+请求级快照；③ 资源隔离：QPS/并发限流、Token 配额、异步队列分池，大租户单独池化，防"一租户打满全平台"；④ 运维：租户 ID 贯穿日志/trace/计费，密钥按租户托管（KMS），压测与告警按租户维度看。

**c 可能追问1**：怎么防止 A 租户知识库被 B 检索到？

**d 追问参考答案1**：召回前 metadata 过滤（tenant_id 强过滤）+ 召回后 ACL 二次校验 + 越权访问审计。以 B 租户身份查 A 租户文档，索引过滤、业务授权、缓存键三处都不能泄漏。

**e 可能追问2**：向量检索命中正确但缓存读出了别家答案，怎么排查？

**f 追问参考答案2**：沿请求链检查 tenant_id、用户 ID、ACL 版本和缓存键组成，确认是否在检索后共用了未按租户隔离的答案缓存。立即失效受影响缓存，修复缓存命名空间和读取时授权校验，加入跨租户回归测试。

**g 设计概念详解**：多租户三层的失败模式不同：数据层泄漏（串台）、配置层串版（A 的 Prompt 用到 B）、资源层挤兑（打满）。缓存是最容易漏的隔离点——检索做了隔离，答案缓存忘了带租户前缀，等于白做。

### 题26｜Agent 的状态机里有哪些状态？★

**a 问题**：Agent 的状态机怎么设计？有哪些状态？

**b 参考答案**：一句话：基础状态+复杂场景状态两类，核心是状态转移、持久化、故障恢复及外部副作用处理。要点：① 基础 11 态：已创建、执行中、等待模型、知识检索中、工具调用中、等待工具结果、暂停中、执行完成、执行失败、用户取消、执行超时；② 复杂场景补充：规划中、反思中、重试中；③ 设计成状态机是生产级要求：便于中断恢复、人工介入、幂等重放；④ 落地三件：持久化（每步落库）+ 状态转移表 + 超时兜底——不要只背枚举。

**c 可能追问1**：Agent 发邮件后进程崩溃，恢复到发邮件前的 checkpoint，会重发邮件吗？

**d 追问参考答案1**：区分内部 checkpoint 与外部副作用。Checkpoint 只恢复 Agent 内部执行状态，不能撤销已发出的支付、邮件或消息。恢复时为邮件查发送回执或按消息幂等键去重，不盲目重发。

**e 可能追问2**：下游系统不支持幂等键，怎么降低重复发送风险？

**f 追问参考答案2**：先在本地以业务 ID 做唯一约束和发送状态机，尽量向下游传可追踪业务标识；超时后优先查询回执或对账。若下游既无去重也无查询能力，无法保证严格不重复，应停止自动重发并转人工核实。

**g 设计概念详解**：状态机的价值是**显式化**：每个状态对应一组合法转移和超时兜底，把"任务执行到哪了"变成可持久化、可恢复、可审计的数据。用户中途取消时：取消信号贯穿调用链，关键节点设检查点；资源回收（终止子任务/释放连接）与结果一致性（半途结果如何标记）都要设计。

### 题27｜企业级 Agent 的技能/工具分层体系怎么设计？★

**a 问题**：企业有几百个工具，工具体系怎么分层？

**b 参考答案**：一句话：三层拓扑——意图路由层→场景聚合层→原子工具层，上层只暴露业务语义，底层保持单一职责和可复用性。要点：① 意图路由层：识别意图并路由到聚合技能，业务入口只暴露这一层；② 场景聚合层：编排多个原子能力完成一个业务场景（"售后处理"=查订单+查规则+发消息），可组合复用；③ 原子工具层：单一职责、接口语义清晰（查订单、发短信、计算），可被任意上层复用；④ 收益：原子能力一次开发多处复用，新增业务只加聚合层，意图路由与实现解耦；⑤ 异常处理：底层本地兜底（默认值/重试），错误码逐层上报，上层拿到可读原因而非裸异常，上报带链路 ID。

**c 可能追问1**：工具数量上百后怎么办？

**d 追问参考答案1**：做工具检索（RAG over tools）——先按意图召回 TopK 工具描述再让模型选，否则 schema 会吃满上下文、模型"变笨"。

**e 可能追问2**：为什么意图路由与实现要解耦？

**f 追问参考答案2**：意图表达（用户怎么说）与实现路径（调哪些工具）变化频率不同——话术常变、工具很少变；解耦后改话术只动路由层，加工具只动聚合层，互不牵连。

**g 设计概念详解**：这是经典的 Portals/Service 组合思想在 Agent 的复刻：原子层保证**可复用**（稳定），聚合层保证**业务语义**（灵活），路由层保证**入口收敛**（可控）。错误处理上"本地兜底+逐层上报"避免裸异常穿越层级。

### 题28｜MCP 和 Function Calling 的边界？★高频

**a 问题**：MCP 和 Function Calling 是什么关系？

**b 参考答案**：一句话：Function Calling 让模型表达工具调用意图；MCP 标准化 Host 与外部能力的连接和调用，Host 将模型调用映射到 MCP 工具。要点：① FC 解决"模型怎么表达要调什么"；MCP 解决"工具怎么标准化接入与治理"（也包括资源、提示模板等协议能力，目前主要用工具）；② MCP 工程要点：工具 schema 规范、鉴权与权限范围、超时与幂等、上下文边界（MCP 上下文与主对话隔离）、调用审计、失败兜底；③ 失败处理：先判定错误类型和执行结果是否确定；可安全重试才重试，敏感操作可能需要人工审批；④ 一图记住：FC=模型输出结构化调用意图；MCP=统一插头（AI 界的 USB-C）；Skills=编排层封装。

**c 可能追问1**：有了 FC 为什么还要 MCP？

**d 追问参考答案1**：生态解耦：N 个工具 × M 个模型从 N×M 适配变成 N+M。MCP 统一了工具的发现（tools/list）、描述和调用（tools/call）协议，工具方和模型方各自对接一次即可。

**e 可能追问2**：MCP Server 返回恶意指令怎么办？

**f 追问参考答案2**：工具输出视为不可信数据——Host 阻断越权工具，工具结果只作数据不提升为系统指令（数据/指令边界）；模拟 MCP Server 权限拒绝和返回恶意指令做回归测试。

**g 设计概念详解**：两个协议解决**不同层面的问题**：FC 是模型能力接口（纵向：模型→应用），MCP 是工具接入标准（横向：应用→工具生态）。类比：FC 像函数声明语法，MCP 像 USB 接口标准。有了 MCP，工具从"每个应用各自集成"变成"即插即用"。

### 题29｜MCP 协议、Skills 与模型如何发现可用工具？★

**a 问题**：模型怎么知道有哪些工具可用？

**b 参考答案**：一句话：三条发现路径——全量注入工具清单、按需检索工具（RAG over tools）、MCP 动态发现（tools/list / 网关注册）；Skills 是"渐进式披露"。要点：① 全量注入：工具少时按协议把 schema 放进 tools 字段或提示上下文，最简单，工具一多就吃满上下文；② 工具检索：工具上百后先按用户意图召回 TopK 工具描述再让模型选（本质 RAG 分类），配合"工具命名+描述+负样本"提升命中；③ MCP 动态发现：Client 连接 Server 后 tools/list 获取能力清单，调用 tools/call；企业级用 MCP 网关集中注册、过滤、鉴权，Agent 不裸连业务系统；④ Skills 渐进式披露：启动时只提供技能名与描述，命中后按需读取 SKILL.md 详细说明；⑤ Skills 与 MCP 分工：MCP=工具箱（连接与调用），Skill=技能手册（一类任务怎么做）；"会调工具 ≠ 会完成任务"。

**c 可能追问1**：工具太多导致模型"变笨"怎么办？

**d 追问参考答案1**：先检索再调用——600 个工具不可能每轮全发。工具注册中心维护描述、权限与版本；按意图召回候选工具，授权过滤后传入模型可见列表；在线追踪误选率。能显著压缩工具描述的 Token 占用并提升选择准确率。

**e 可能追问2**：工具检索漏掉关键工具时，怎么回退而不泄露无权限工具？

**f 追问参考答案2**：先按当前身份和租户权限生成可见工具集合，再在集合内检索；召回信心不足时扩大合法候选、使用确定性路由或请求澄清。权限过滤必须在检索和展示之前执行，不能为兜底暴露不可用工具。

**g 设计概念详解**：发现机制的核心矛盾是**上下文成本 vs 可见性**：全量注入可见性最好但 Token 爆炸；检索省 Token 但可能漏。工程解法是分层：高频工具常驻，长尾工具检索；Skill 命中率四招——描述写清触发场景、建 Skill Tree 分层路由、加负样本说明何时不用、召回+重排。

### 题30｜Agent 死循环与 Loop 七大风险怎么防？★高频

**a 问题**：Agent 死循环怎么防？Loop 有哪些风险？

**b 参考答案**：一句话：死循环根因是"重复动作+无收敛判据+反馈缺失"，用步数上限、重复检测、强制重规划、熔断降级四道闸门防。要点：① Loop 七大风险点：无限迭代、重复调用、上下文膨胀、成本失控、状态漂移、结果未收敛、反馈假象；② 防控手段：最大步数/轮次上限；失败轨迹记录+工具黑名单+强制重规划+降级兜底；阈值控制+记忆裁剪+校验策略；高危操作人工确认；③ 更细判据：同一工具+同一参数连续 N 次→判定无进展；连续两轮计划无变化→强制重规划；④ 治理总纲：先明确失效定义与场景，再渐进式排查分层止损，别一上来就中断业务。

**c 可能追问1**：max_steps 设多少合适？

**d 追问参考答案1**：没有普适值——按任务正常轮次 P95 上浮 2–3 倍，并配合无进展检测，而不是只靠一个大数字。

**e 可能追问2**：同一工具参数相同但数据实时更新，怎么避免误判死循环？

**f 追问参考答案2**：重复判定不只看工具名与参数，还要看资源版本、返回内容、时间窗口和任务进展。实时轮询可允许相同参数但限制频率和持续时长；结果无变化且无新增证据才触发重规划或熔断。例：Agent 连续十次搜索同一查询结果毫无变化——按动作签名与结果摘要检测无进展，触发查询改写或人工终止。

**g 设计概念详解**：死循环是**收敛性**问题：Agent 没有天然的停止条件，必须外部注入收敛判据（无进展检测、成本预算、目标达成校验）。"反馈假象"最隐蔽——工具每次返回 200 但内容对任务无增量，看起来在工作其实在空转。

### 题31｜Function Calling 底层原理与线上工程坑怎么答？★

**a 问题**：FC 的底层原理是什么？线上有哪些坑？

**b 参考答案**：一句话：FC 的核心是模型依据工具说明生成结构化调用意图，执行仍在应用侧；不同模型通过训练、提示模板和可选的约束解码实现，不能统一归结为 SFT+约束解码。要点：① 本质：模型不执行代码，只产出调用意图；函数签名/参数 schema 转成模型可理解格式，执行层解析调用、回填结果；② 原理层：工具调用能力通常由训练和提示模板共同支持，部分系统用 grammar-constrained decoding 约束语法；语法合法不代表业务参数正确，仍需 schema、语义和权限校验；③ 与 Tool Calling 的关系：同一阵营两个视角——FC 偏协议机制（JSON 前后衔接），Tool Calling 偏动作与步骤（工具设计、错误处理）；④ 线上四大坑：schema 膨胀（工具多了上下文吃满）、参数幻觉（必须有校验层）、结果回填（工具输出要格式化后喂回）、超时/失败降级；⑤ 流式 JSON：工具调用参数以增量片段返回，必须收全并通过 schema 校验后才能执行；增量解析只用于进度展示。

**c 可能追问1**：权限边界放哪？

**d 追问参考答案1**：转账类高危工具，权限放后端不放模型——模型只产意图，执行层鉴权。

**e 可能追问2**：一次对话工具调用轮次多少算正常？

**f 追问参考答案2**：没有统一正常轮数；轮次偏多可能源于任务复杂度、工具粒度、规划或失败重试，应结合任务基线诊断；工程上仍要设上限防失控。

**g 设计概念详解**：答题模板：原理（是什么/怎么训练）+工程（schema/校验/回填/降级）+案例（项目里踩过哪个坑）。流式坑的本质：增量片段是**不完整 JSON**，半截解析执行等于执行幻觉参数——所以执行前必须缓冲收全再校验。
