## 第五章 记忆与上下文管理

### 题32｜Agent 的记忆机制怎么设计？★高频

**a 问题**：Agent 的记忆机制怎么设计？

**b 参考答案**：一句话：记忆分短期和长期；短期维持当前任务状态，长期保存跨会话可复用信息，原始记录、摘要和结构化事实分开管理。要点：① 短期/工作记忆：当前任务上下文+状态（目标、槽位、已执行步骤），随任务结束释放；② 长期记忆按内容分三类：情景（具体事件）、语义（事实与偏好）、程序（方法与流程）；③ 记忆三大价值：状态延续（接着聊）、效率（不重复计算省 Token）、个性化（积累偏好）；④ 记忆不是越多越好：变大→加载 Token 上涨，需分层管理+遗忘机制（过期清理/价值衰减）；⑤ 工程存储四件套：原文/事件日志（可回源）+摘要（进上下文）+结构化 KV（可过滤）+向量索引（可语义召回），四者职责不同别混成一份。

**c 可能追问1**：为什么不能只用向量库？

**d 追问参考答案1**：向量检索解决"相似"，解决不了精确事实、时间顺序、权限与冲突更新——合同号、有效期这类精确事实必须走结构化存储；向量库只是记忆系统的一路召回索引。

**e 可能追问2**：用户偏好从"无糖"改成"正常糖"，旧记忆怎么失效而不误删事件记录？

**f 追问参考答案2**：将当前偏好作为带版本与生效时间的事实记录，用户明确更改后把旧偏好标记失效并写入新值；历史事件仍保留其当时的时间语境。读取"当前偏好"只取有效版本，并遵守删除和保留策略。

**g 设计概念详解**：记忆系统的设计哲学是**按用途分库**：回源用日志、上下文用摘要、过滤用 KV、语义召回用向量。混用会产生"用向量库存合同号"式的错配——能搜到相似的，但无法精确更新和校验。

### 题33｜记忆如何写进去（写入时机与信号）？★

**a 问题**：长期记忆什么时候写入？怎么触发？

**b 参考答案**：一句话：三块触发——对话结束做总结抽取、事件触发即时写入、后台定期整理；再加一层冲突检测。要点：① 对话结束时总结抽取：如"下周去东京出差"抽成结构化记忆（事项/时间/地点），不存整段聊天；② 事件触发写入：用户明确说"记住，我对花生过敏"是最高优先级信号，立刻落库——先检查用户授权、数据敏感级别、保存策略和存储权限，满足后结构化写入、冲突检测、版本更新；③ 后台定期整理：空闲时归并、去重、合并同类项；④ 冲突检测：三年前喜欢甜咖啡、昨天说戒糖→更新旧记忆并打新时间戳，不是追加一条矛盾记录；⑤ 写入前质量校验：防脏数据、冲突事实、模型错误推断进入长期记忆（记忆污染会污染后续所有决策）。

**c 可能追问1**：写入策略用规则还是模型抽取？

**d 追问参考答案1**：两条路线——规则硬阈值（明确说记住/个人属性/任务闭环结论）确定性高但死板；模型自主抽取灵活但易漏易脏。生产常用规则兜底+模型抽取。

**e 可能追问2**：怎么验证记忆写得对？

**f 追问参考答案2**：构造"三个月前说过的偏好"类问题，测召回率与冲突更新正确率；再测"该忘的有没有忘"（过期数据是否清理）——记忆评测是闭环意识的体现。

**g 设计概念详解**：写入时机的本质是**信噪比与时效**权衡：实时抽取贵且噪声多，批量抽取省但有延迟，显式指令（"记住…"）零延迟零歧义优先级最高。冲突更新用"版本+生效时间"而非覆盖删除，保留审计能力。

### 题34｜长期记忆持续增长，怎么避免存储失控？

**a 问题**：长期记忆无限增长怎么办？

**b 参考答案**：一句话：用价值打分、摘要、冷热分层、去重和配额控制记忆增长；原文保留期限由追溯需求和数据治理规则决定。要点：① 按价值打分（重要性/访问频率/时间衰减）决定保留层级；每用户/每项目设配额；② 定期摘要+去重合并；冷数据下沉对象存储，热数据留检索库；③ 摘要和原文用途不同：是否保留原文由追溯需求、保存期限、隐私与合规决定；需要溯源时保留可验证来源，不默认永久保存全部原始记录；④ 上线后监控两件事：存储增长速度、召回命中率（只压不查会"省了钱但变笨"）；⑤ 核心四动作：压缩、分层、检索、淘汰。

**c 可能追问1**：删了会不会丢信息？

**d 追问参考答案1**：按保留策略冷热分层；允许保留的原文可按需回源，过期或用户依法要求删除的数据必须落实删除——删除要覆盖索引、缓存与备份，否则等于没删。

**e 可能追问2**：怎么判断一段记忆"有价值"？

**f 追问参考答案2**：三维打分——重要性（对用户目标的影响）、访问频率（被召回次数）、时间衰减（越久权重越低）；高价值长期保留在热层，低价值衰减下沉。

**g 设计概念详解**：记忆治理与数据治理同构：分级（敏感/内部/公开）、生命周期（热/温/冷/归档）、合规（可删除权）。Agent 特有的一点是**召回质量**也是治理目标——压缩过度导致"变笨"与存储爆炸同样致命。

### 题35｜上下文压缩：什么时候做？优先压缩哪部分？★高频

**a 问题**：上下文压缩的时机和优先级怎么定？

**b 参考答案**：一句话：预算水位触发；先删冗余闲聊，再修剪工具原始输出（保留协议配对约束），最后才摘要阶段性交互。要点：① 时机：每次调模型前估算 Prompt Token，预留回复与工具返回空间；逼近水位就在下一轮推理前压缩，不等超限报错；② 优先级四步：剔除冗余过期闲聊→修剪冗长工具原始输出（保留结论与关键字段）→已完成的调用轨迹整体摘要或转结构化状态（保留原始消息时维护调用与返回的合法配对）→最后对已完成的阶段性交互做文本摘要；③ 绝对不能丢：当前任务目标、约束条件、尚需继续执行的工具调用状态、关键证据链（引用来源）；④ 压缩后校验：模型还能否回答"当前任务是什么、已经做了什么"；必要时把关键事实显式锚定在系统提示里。

**c 可能追问1**：网页抓取返回 5 万 Token 挤占上下文，怎么处理？

**d 追问参考答案1**：保留工具调用与返回的合法消息结构，长内容落对象存储，注入摘要、关键证据与来源指针，压缩后回归测试。验证：注入大量重复文本的工具返回后，任务目标、关键数值、来源链接和未完成工具调用配对均可恢复。

**e 可能追问2**：引用证据被摘要掉了，怎么恢复可审计的答案？

**f 追问参考答案2**：摘要中保留来源文档 ID、版本、页码/段落和原文定位指针，审计时从原始证据库回源取出支持片段。若来源已不可取得，标记不可核验——不能把摘要当原始证据。

**g 设计概念详解**：压缩优先级的依据是**信息对下一步决策的边际价值**：闲聊为零（先删）、工具原始输出有冗余（可压）、目标与约束无穷大（永不删）。工具调用配对是协议约束——拆散会导致二次推理错乱。

### 题36｜多轮对话的上下文怎么管（指代丢失问题）？★高频

**a 问题**：多轮对话里"退款到哪了"的"它"丢了，怎么管上下文？

**b 参考答案**：一句话：四层管控——状态管理、工具调用补全、生成端上下文、执行缓存。要点：① 状态管理层：维护任务结构化状态（任务域、关键实体、用户意图轨迹、已执行工具结果），更新状态而不是追加聊天文本；② 工具调用层：每轮调用前结合任务状态把参数补全为完整可执行参数，补全后做可信度校验，低可信度向用户澄清；③ 生成端上下文层：只放最近 n 轮相关对话+工具执行结果，更早历史压成任务事实摘要放系统提示；历史摘要作为有明确来源和信任级别的上下文注入，不无差别提升为系统级指令；④ 执行缓存层：同一任务域且实体未变更→复用上一轮结果，切换任务或实体变化才重新调用工具。

**c 可能追问1**：指代丢失有哪几种成因？

**d 追问参考答案1**：三种——实体未入状态（订单 ID 只存在于上轮对话没进状态对象）、任务切换未清理（旧任务实体污染新任务）、摘要丢了指代对象（压缩时把被指代的名词删了）。能说出成因比背四层更有说服力。

**e 可能追问2**：补全参数后怎么判断可信？

**f 追问参考答案2**：来源追溯（状态里有没有这个实体）+ 一致性校验（实体属性与任务匹配）+ 置信度阈值；低于阈值反问用户确认，而不是猜一个执行——猜错执行是事故，反问只是体验损失。

**g 设计概念详解**：指代丢失的本质是**会话状态与对话历史分离失败**：把聊天记录当唯一状态源，指代对象就只存在于"上一轮原文"里，一压缩就丢。解法是实体抽取入状态（第一次出现时就入表），后续所有指代解析走状态不走历史。

### 题37｜高效上下文维护方案怎么设计？★

**a 问题**：高效的上下文维护方案怎么设计？

**b 参考答案**：一句话：分层——系统提示、任务状态、最近对话、检索证据、长期记忆各占一层；再加摘要、去重、过期和预算控制。要点：① 分层配额：先给每层定预算（如系统提示 10%、状态 20%、对话 30%、证据 40%），超了按优先级裁；② 摘要：按话题/时间段滚动，保留实体、约束、结论，删寒暄与重复确认；③ 去重与过期：同一事实只留最新；任务结束清理临时上下文，长期记忆走单独治理流程；④ 回源：细节不常驻上下文，留指针（文档 ID/事件 ID），需要时再取；⑤ 量级认知：几万到几十万 Token 是常态，但成本、延迟、注意力噪声随长度上升——长上下文不等于无限记忆。

**c 可能追问1**：上下文分层的判断标准？

**d 追问参考答案1**：一句话——"这段信息对当前这一步决策有什么用？"答不上来就删。上下文工程的目标是让模型在对的时机看到对的信息，不是塞满窗口。

**e 可能追问2**：上下文怎么分层（八股版）？

**f 追问参考答案2**：五块——系统提示/任务状态/最近对话/检索证据/工具输出，直接落到这五块比说"用滑动窗口"具体。

**g 设计概念详解**：分层配额是**预算思维**：每类信息有明确 ROI（系统提示影响全部轮次、闲聊只影响当轮），按 ROI 分配 Token 预算，超预算从低 ROI 层裁起。

### 题38｜信息该存平台数据库还是本地？

**a 问题**：用户数据存云端还是本地？

**b 参考答案**：一句话：云端便于同步、权限与统一治理；本地适合隐私、离线、低延迟；成熟方案是分层存储+数据主权可控。要点：① 云端：多端同步、集中权限、统一备份与审计；代价是合规风险与网络延迟；② 本地：隐私合规、离线可用、低延迟（端侧记忆）；代价是多端一致性与备份麻烦；③ 分层：敏感原文本地/私有化，索引与元数据上云；跨端只同步摘要与引用，原文按需拉取；④ 决策因素：数据分级（公开/内部/敏感/个人信息）、合规要求（出境、留存期限）、离线场景、团队运维能力；⑤ 数据主权：用户可导出、可删除、可关闭记忆；删除要覆盖索引、缓存与备份。

**c 可能追问1**：为什么不全本地？

**d 追问参考答案1**：模型能力、更新与运维成本——端侧跑不动强模型，记忆治理（去重/冲突检测）需要的服务端算力本地不具备。

**e 可能追问2**：为什么不全云？

**f 追问参考答案2**：合规（个人信息出境）、断网可用性、延迟（每轮记忆召回走网络）。

**g 设计概念详解**：这是经典的数据分级问题：按敏感度决定物理位置，按访问模式决定形态（原文 vs 摘要 vs 指针）。Agent 特有约束是"记忆是推理的输入"——数据在哪、以什么粒度可被召回，直接决定能力边界。

### 题39｜Agent 凭啥记住三年前说的话？★

**a 问题**：Agent 怎么记住三年前的对话？

**b 参考答案**：一句话：不是"记性好"，是一套工程链路——分类存储、写入时机、冲突检测、混合检索、上下文压缩、遗忘与评测。要点：① 只答"向量数据库+RAG 检索"会被追穿：那只解决"存和取"，没解决"记什么、什么时候记、冲突怎么办、忘了怎么办"；② 覆盖六件事：记忆分类、写入时机、冲突检测、混合检索策略、上下文压缩、遗忘机制与评测方法；③ 落地细节：时间衰减+重要性加权+关键词/向量混合召回；召回后再用模型做相关性过滤；④ 面试考察三层：结构化思维（能不能分层）、踩坑经验（冲突更新/压缩丢信息/检索不能只靠相似度）、闭环意识（怎么验证它记得对、该忘的有没有忘）。

**c 可能追问1**：记忆评测怎么设计？

**d 追问参考答案1**：构造"三个月前说过的偏好"类问题，测召回率与冲突更新正确率；再构造"应该遗忘的"（过期任务、被撤销的偏好）测误召回——记忆系统要双向验证。

**e 可能追问2**：RAG 召回和记忆召回有什么区别？

**f 追问参考答案2**：RAG 召回的是相对准确稳定的外挂知识，召回即用；记忆召回要做"召回推理"——候选记忆先让模型判断与当前问题是否真相关、是否冲突，过滤后再入上下文。记忆还要额外关注个性化、跨会话更新与遗忘。

**g 设计概念详解**：长期记忆 = 存储（分层）+ 治理（写入/冲突/遗忘）+ 检索（混合召回+推理过滤）三个子系统。多数人只答第一个，区分度在后两个。

### 题40｜Agent 记忆的三大分类（情景/语义/程序）？★高频

**a 问题**：Agent 记忆分哪三类？

**b 参考答案**：一句话：工程上分情景记忆（Episodic）、语义记忆（Semantic）、程序记忆（Procedural）；情景记忆不是原始日志的同义词。要点：① 情景记忆：保存带具体时间、场景与上下文的经历或事件表示——可由对话、工具执行等日志提炼而来，回答"什么时候、发生了什么"；量大、时序性强，按合规与追溯需求决定是否保留原文；② 语义记忆：提炼沉淀的事实、用户偏好、常识，脱离具体对话长期固化（"用户不吃辣"），由情景记忆萃取而来，多用结构化 KV+向量索引；③ 程序记忆：技能与流程（"查库先校验参数再执行 SQL"），回答"这类任务该怎么做"，常以 Skill/SOP/工具编排形式存在；④ 口径注意：认知科学中陈述性记忆（Declarative）通常包含情景与语义两类；Agent 工程三分法应称"情景/语义/程序"，别把陈述性与语义记忆当同义词。

**c 可能追问1**：情景记忆和原始日志是一回事吗？

**d 追问参考答案1**：不是。原始日志是逐条交互记录，情景记忆是有时间、参与者与事件语境的经历表示，可以由日志归纳而来。原始工具执行日志是事件证据，是否转化为情景记忆取决于其是否形成带情境的可复用事件表示。

**e 可能追问2**：工作记忆算哪类？

**f 追问参考答案2**：它是短期的、任务级的，不在这三类长期记忆里；把它和短期上下文放在一起讲更准确。

**g 设计概念详解**：分类的工程价值在于**存取方式不同**：情景按时间线组织（可回溯）、语义按实体组织（可查询更新）、程序按任务模式组织（可复用执行）。案例：售后纠纷（情景）+ 长期饮食偏好（语义）+ 售后 SOP（程序）分开存储，操作流程才不会被误写成用户偏好。

### 题41｜Agent 记忆的完整工作链路？★高频

**a 问题**：记忆系统的完整链路是什么？

**b 参考答案**：一句话：萃取→分层存储→有效召回→召回推理→更新与遗忘，五环闭环。要点：① 记忆萃取：从原始对话、工具调用记录、事件日志提取可复用记忆（情景事件、语义事实、操作经验），做摘要、提关键信息、过滤噪声，产出结构化条目并重要性打分——坑：什么都存→冗余、召回噪声；② 分层存储：情景存事件表示、语义存事实偏好、程序存策略技能；原始日志独立存储支持追溯，向量索引用于辅助检索，不等于记忆本身；③ 有效召回：不只靠向量相似度——向量语义+时间衰减+重要性权重综合打分；坑：单纯相似度会召回大量"语义近但无关"的记忆；④ 召回推理（面试官重点）：候选记忆不直接进 Prompt，先让模型做二次判断——与当前问题是否真相关、是否冲突，过滤后再整理入上下文；⑤ 更新与遗忘：旧记忆更新、冲突合并；不重要记忆衰减/过期，避免无限膨胀。

**c 可能追问1**：第 4 步为什么重要？

**d 追问参考答案1**：它是区分"用过 RAG"和"做过记忆系统"的地方——RAG 召回的外挂知识相对准确稳定；记忆召回的候选可能有冲突、过时、与当前任务无关，必须再判断。

**e 可能追问2**：召回打分怎么设计？

**f 追问参考答案2**：向量语义相似度 + 时间衰减（越新越相关）+ 重要性加权（高价值优先）三路融合打分，TopK 后交给模型过滤。

**g 设计概念详解**：五环对应"写入→存储→读取→过滤→治理"的生命周期。最容易缺的是第 4 环（召回推理）和第 5 环（遗忘）——前者导致脏记忆污染回答，后者导致存储和召回质量随时间劣化。

### 题42｜长期陪伴型 AI：第 100 轮还记得第 1 轮，怎么设计？★

**a 问题**：长期陪伴型 AI 怎么记住第 1 轮的关键信息？

**b 参考答案**：一句话：不能靠全量历史，要靠分层摘要+关键事件时间线+偏好表+多路召回，再用一致性校验兜底。要点：① 分层摘要：最近 N 轮原文、更早按话题/时间段滚动摘要、再早只留一句话事件+指针（可回源）；② 关键事件时间线：把"第一次见面、用户换工作、养了猫"这类高价值事件单独结构化存储（时间+事件+情绪/偏好标签），这是"记得第 1 轮"的核心抓手；③ 角色卡+偏好表：人设、称呼、禁忌、喜好单独维护，每次生成都注入，保证第 100 轮人设不漂；④ 多路召回：当前话题相关（向量）+时间最近（recency）+重要性高（importance）三路融合，再经模型过滤；⑤ 一致性校验：回答前检查是否与已知事实冲突（用户已戒烟就不能再推荐烟），冲突时以新事实为准并更新记忆；⑥ 成本控制：长期记忆不每轮全量进上下文，只进"本轮召回+人设+事件摘要"。

**c 可能追问1**：第 1 轮的细节怎么保证不丢？

**d 追问参考答案1**：原文留档+事件指针，需要时回源检索——只靠摘要必然丢细节。

**e 可能追问2**：人设怎么防漂移？

**f 追问参考答案2**：角色卡作为系统提示每轮注入（不是靠历史记忆"想起"人设）；回答后抽样校验与角色卡的一致性。

**g 设计概念详解**：陪伴型记忆的特有设计是**高频注入 vs 低频回源**：人设与偏好每轮进上下文（高频小体量），事件原文存档按需回源（低频大体量）。这与人记忆的"性格恒定、往事翻起"同构。

### 题43｜共享 vs 私有记忆架构怎么设计？★

**a 问题**：共享记忆和私有记忆怎么划分？

**b 参考答案**：一句话：难点不是分类存储，而是边界划分、权限管控、冲突处理、数据淘汰——只做标签分离必然串台。要点：① 私有 memory：个性化与隐私隔离，单人可读，动态清理旧数据；② 共享 memory：复用，统一维护、所有授权用户可读（企业知识、团队规范）；③ 优先级规则：私有内容优先、共享内容兜底，但不能覆盖业务规则、权限要求或权威事实；冲突时按业务裁决（通用知识用共享、个人偏好用私有）；④ 权限：读按角色/租户过滤，写按 owner 限制；共享记忆的写入要走审核，避免污染所有人；⑤ 淘汰：私有按价值打分+过期清理；共享按版本与有效期管理，旧版本下线而不是直接删。

**c 可能追问1**：三名 Agent 共享项目事实，但只有财务 Agent 能读付款信息，怎么设计？

**d 追问参考答案1**：共享区与私有区分别存储；读写按身份、租户、项目和字段级 ACL 授权，写入附来源和版本。验证：让非财务 Agent 尝试读取付款信息——共享记忆检索前实施 ACL 过滤，响应及缓存均不能出现受限字段。

**e 可能追问2**：其他 Agent 把私有结果粘贴进共享摘要时怎么阻止？

**f 追问参考答案2**：共享前对摘要及字段做数据分类、来源标签与 ACL 校验；私有数据采用不可传播标记，未经授权的内容在服务端过滤，而不是由总结模型自行判断。共享记忆保存权限继承关系，权限变化时同步失效索引和缓存。

**g 设计概念详解**：共享/私有是**信任域**问题：私有域信任单用户，共享域信任组织，混合内容（含私有片段的共享摘要）属于降级私有——必须经标记+服务端过滤才能升级。真实冲突样例：同一客户共享库里是 A 等级、私有备注里是 B 等级——按"哪个是权威来源"裁决而非简单合并。

### 题44｜多智能体记忆：核心目标是什么？

**a 问题**：多 Agent 共享记忆，核心目标是什么？

**b 参考答案**：一句话：目标不是"都存下来"，而是让每个 Agent 在合适的时候拿到合适的那部分，同时不串、不脏、不膨胀。要点：① 核心仍是压缩、分层、检索、淘汰，但多了一层"归属"：谁的记忆、谁能读、谁能写；② 三种共享形态：全局共享（用户目标/任务状态）、角色私有（各自的工作草稿）、只读共享（企业知识/规范）；③ 主要风险：写入冲突（两个 Agent 同时改同一条）、上下文污染（A 的草稿被 B 当事实）、权限越界（读到不该读的租户数据）；④ 工程解法：记忆带 owner/task_id/版本号；写入走 CAS 或单写者；读取按权限过滤；跨 Agent 交接只传结构化摘要。

**c 可能追问1**：两个 Agent 同时改同一条记忆怎么办？

**d 追问参考答案1**：CAS 乐观锁（带版本号提交，过时拒绝）或单写者模式（一个 Agent 独占写权）；冲突时按"哪个 Agent 的领域归属"仲裁。

**e 可能追问2**：跨 Agent 记忆交接传什么？

**f 追问参考答案2**：只传结构化摘要（任务+上下文+当前状态），不传完整记忆库——每个 Worker 只需要与自己的子任务相关的记忆切片。

**g 设计概念详解**：多 Agent 记忆 = 单 Agent 记忆 + **归属与并发控制**。A 的草稿被 B 当事实是典型事故——解法是信任级别标记（草稿=低信任、验证过的事实=高信任），下游按信任级别决定能否作为决策依据。

## 第六章 多智能体协作

### 题45｜多 Agent 协作除了顺序执行还有哪些模式？★高频

**a 问题**：多 Agent 协作有哪些模式？

**b 参考答案**：一句话：并行、仲裁、主从、多级委托四类；再往上是按任务依赖和并发收益做组合。要点：① 串行顺序流：任务有前后依赖（写代码→审查），稳、不乱；② 并行执行：多个独立子任务同时做（查库+生成图表+整理素材），提升速度；③ 仲裁模式：多个 Agent 各自出方案，由裁判 Agent 按证据与规则裁决冲突（裁判不负责分任务），关键步骤留人工入口；④ 主从模式：主控 Agent 当大脑，分解、分发、汇总；优点是逻辑清晰、便于监控；缺点是主控单点——需状态同步、热备与故障转移；⑤ 多级委托：战略规划 Agent→中层中控→底层执行，树状上下行，同层不直接通信；⑥ orchestrator-worker 典型实现：调度者拆子任务（每个可独立验收）→worker 并行执行（上下文互不污染）→结构化交接（任务、上下文、当前状态三字段）→调度者聚合去重；必须配中止条件：超时+Token 预算上限。

**c 可能追问1**：其中一路 worker 失败，最终报告继续、标注缺口还是停止？

**d 追问参考答案1**：依据任务的必需依赖与失败策略：缺少核心证据就停止或请求补齐；非关键分支失败可继续但显式标记缺口、降低结论置信度。结果聚合器记录每条分支状态，禁止把不完整结果伪装成全部完成。

**e 可能追问2**：工程实现三件套是什么？

**f 追问参考答案2**：消息队列（带会话 ID/任务 ID/步骤序号保证有序）+统一状态中心（执行前读最新、执行后立刻更新）+失败重试两次后进死信队列人工排查。

**g 设计概念详解**：模式选择决定**失败传播路径**：串行失败一步停一步（易定位）、并行失败部分可用（要聚合策略）、主从失败靠主控兜底（有单点）、仲裁失败靠证据裁决（最慢但最稳）。

### 题46｜多智能体编排拓扑、通信与兜底？★

**a 问题**：多 Agent 的拓扑、通信机制和失败兜底怎么设计？

**b 参考答案**：一句话：三种拓扑（星型编排、平等协作、层级调度）+结构化 handoff+超时死信兜底。要点：① 星型调度（orchestrator-worker）：调度者拆任务分发，worker 并行执行，上下文互不污染，适合任务能清晰拆分；② 平等协作（peer）：无中心，Agent 间直接协商，适合探索型、写作型任务，但要解决一致性与死锁；③ 层级调度：适合更大规模任务，上层规划、下层执行，同层不直接通信；④ 通信机制：结构化 handoff 固定三字段——任务、上下文、当前状态；再决定用"共享状态"（强一致、短链路）还是"消息传递"（解耦、异步、长链路）；⑤ 失败兜底：worker 卡住怎么发现（超时检测）→怎么兜底（终止条件/重试/死信队列/降级）→怎么复盘（失败轨迹进评测集）。面试考四点：编排拓扑、通信机制、选型判断、失败处理。

**c 可能追问1**：共享状态会不会冲突？

**d 追问参考答案1**：会——版本号/CAS+单写者；写前读最新状态，提交带版本号，过时拒绝。

**e 可能追问2**：报告任务包含独立的市场调研、财务分析和综合写作，怎么编排？

**f 追问参考答案2**：前两者并行，合并时验证证据来源和口径，最终写作必须等待两者完成，失败分支单独降级。验证：市场与财务一个超时一个成功——调度器记录部分完成状态，综合写作明确缺失证据并决定重试或降级。

**g 设计概念详解**：拓扑的本质是**控制权分布**：星型集中（可监控可单点）、peer 分散（无单点但难协调）、层级分层（规模化的折中）。通信选型看一致性需求与时延容忍：共享状态同步强一致，消息传递异步解耦。

### 题47｜生产级多 Agent 意见冲突怎么解？★高频

**a 问题**：多个 Agent 结论冲突怎么办？能投票吗？

**b 参考答案**：一句话：别答"少数服从多数"——主从分歧靠主 Agent 裁决并重估反对意见，写入分歧靠锁与路径检测，投票只能做辅助。要点：① 同源模型容易集体盲从：几个 Agent 用同一个底座，投票只是放大同一种偏差，所以"投票/裁判 Agent"不是生产级答案；② 主从分歧：主 Agent 拥有最终裁决权，但必须把 Sub-agent 的反对意见当事实输入重新评估；超出编排权限交人工；③ 写入分歧（Team 模式）：协调者系统提示词明确"只读任务随意并行，写任务同一批文件一次只分配给一个 worker"；④ CAS 乐观锁：worker 提交变更带版本号，过时拒绝提交；抢同一任务直接抛认领冲突；配合路径重叠检测（重叠目录触发冲突警告）；⑤ 投票的正确用法：只用于"多方案探索"的初筛，且要保证视角差异（不同模型/不同检索源/不同提示词），最终仍由证据与规则裁决。

**c 可能追问1**：两个审核 Agent 对合同风险给出相反结论，怎么仲裁？

**d 追问参考答案1**：用证据、规则优先级和复核机制仲裁——条款原文、适用规则版本、证据强度裁决；不能简单按 Agent 数量投票；仍有歧义交人工律师（法务复核）。

**e 可能追问2**：如果两方引用的是同一份过期制度，投票为什么无效？

**f 追问参考答案2**：投票不能修复共同来源错误——多个 Agent 可能共享同一份过期证据。仲裁应比较来源独立性、文件版本、生效时间和权威等级，必要时回查现行制度；无法验证就标注冲突并交人工。

**g 设计概念详解**：冲突解决的核心是**证据裁决而非人数裁决**。总结句：主从分歧靠全局裁决，质检对抗靠单测物证与 DAG 依赖，写入分歧靠锁与路径检测。投票的前提是视角独立性——同源模型投票是伪独立。

### 题48｜多个 AI Agent 之间如何通信与协作（A2A）？★高频

**a 问题**：Agent 之间怎么通信协作？A2A 是什么？

**b 参考答案**：一句话：三层逻辑——服务发现（谁能干）、能力对齐（怎么对接）、状态交接（接力棒怎么传）。要点：① 服务发现：A2A 用 Agent Card 描述能力、接口与安全要求；发现可通过 well-known 地址、注册中心或预配置卡片，不要求广播；企业用注册中心/网关维护能力目录——注意微服务注册 IP+端口，A2A 注册的是能力元数据；② 能力对齐：用标准 schema 约定输入输出契约（输入格式是什么、输出保证 JSON 吗），消除自然语言模糊性，防幻觉翻倍；③ 状态交接：不只传数据，要传"接力棒"——任务+上下文+当前状态+下一步能力要求；④ A2A vs MCP：MCP 解决 Agent↔工具/数据的连接（纵向接能力），A2A 解决 Agent↔Agent 的协作（横向接同伴）；⑤ 工程约束：消息带 task_id/trace_id、幂等、超时、重试与死信；跨组织协作还要 identity 与授权。

**c 可能追问1**：A2A 是又一个 Function Calling 吗？

**d 追问参考答案1**：不是——FC 是模型输出格式（模型→应用的调用意图），A2A 是服务间协议（Agent↔Agent 的协作规范），层次不同。

**e 可能追问2**：Agent A 超时但 Agent B 仍在执行，怎么恢复或取消？

**f 追问参考答案2**：用 task_id、状态查询、心跳与超时租约区分"调用端超时"和"远端任务失败"。恢复时查询 B 的任务状态；取消需发送协议支持的取消请求并确认结果，不能假设超时自动终止，也不能直接重复创建任务。

**g 设计概念详解**：A2A 与 Orchestrator-Worker 的区别：固定调度器派活 vs Agent 自主发现协作方。A2A 的核心价值是**能力市场的标准化**——任何 Agent 都能按能力标签找到并安全调用其他 Agent，就像微服务生态里的服务发现，但注册的是"能力"而非"地址"。

### 题49｜执行 Agent 发现计划有误时，该照做还是拒绝？

**a 问题**：Executor 发现 Planner 的计划有误，照做还是拒绝？

**b 参考答案**：一句话：都不对——要校验前提，失败就拒绝并带证据反馈，触发重规划；高风险场景直接升级人工。要点：① 四层作答：执行契约（入口可靠：字段/来源/版本/权限/时间记录清楚）→前提校验（状态确认、失败兜底）→拒绝反馈（带证据回传、重规划闭环）→轨迹评测（拒绝是否合理可复盘）；② 反例：Planner 要求删除旧索引，Executor 查到新索引还没预热完成，照做就是线上事故；③ 踩坑警示：把"相关信息"当充分证据、把"调用成功"当业务成功；④ 拒绝不是罢工：给出"哪条前提不满足+建议的替代路径+风险等级"，Planner 才能改。

**c 可能追问1**：子 Agent 的独立判断边界在哪？

**d 追问参考答案1**：边界是"可验证的前提"：Executor 对自己执行域内可查询的事实（索引状态、数据版本）有独立判断权；超出自己域的（业务优先级、全局策略）反馈给 Planner，不擅自决策。

**e 可能追问2**：怎么防止 Executor 借"计划有误"逃避任务？

**f 追问参考答案2**：拒绝必须带证据（查询结果、版本号、时间戳）并留轨迹；Reviewer 复盘拒绝是否合理——无证据的拒绝视为执行失败。

**g 设计概念详解**：这题考的是**分权与问责**：Planner 有规划权，Executor 有执行域事实的判断权；拒绝机制让错误计划在执行前被拦截，是"分层校验"在多 Agent 里的体现。

### 题50｜Agent 的实现方式和编排范式有哪些？

**a 问题**：Agent 实现方式和编排范式有哪些？

**b 参考答案**：一句话：简单固定流程→Planner+Executor→多 Agent 协作；编排范式有 ReAct、状态机、工作流、DAG、事件驱动。要点：① 实现方式按复杂度递进：固定流程（workflow）→单 Agent 循环（ReAct）→Planner+Executor→多 Agent 协作；② 编排范式：ReAct（边想边做）、状态机（显式状态与转移）、工作流（固定节点）、DAG（依赖编排）、事件驱动（解耦与异步）；③ 选型依据：任务确定性、是否需要人工介入、失败恢复要求、团队维护成本；④ 工程最重要三条：可观测、可回滚、可限制轮次。

**c 可能追问1**：状态机和 DAG 有什么差别？

**d 追问参考答案1**：状态机强调状态与转移（单线程的生命周期管理），DAG 强调依赖与并行（多任务的调度关系），二者常组合使用——每个任务是状态机，任务之间是 DAG。

**e 可能追问2**：什么时候用事件驱动？

**f 追问参考答案2**：需要解耦与异步的场景——长链路协作、多消费者广播、跨系统联动；事件驱动牺牲可读性换扩展性，调试更难，要配全链路 trace。

**g 设计概念详解**：范式是**控制流的不同表达**：代码写死（workflow）确定性最高，模型驱动（ReAct）灵活性最高，中间是状态机/DAG 用结构约束模型自由度。

### 题51｜多 Agent 的职责拆分怎么讲？★

**a 问题**：多 Agent 怎么拆职责？

**b 参考答案**：一句话：规划、检索、执行、校验四个角色各司其职；共享状态只放全局信息，阶段产物挂在节点下。要点：① 角色拆分：规划 Agent（拆解与调度）、检索 Agent（找证据）、执行 Agent（调工具/写结果）、校验 Agent（质量与合规）；② 共享状态设计：全局共享放用户目标、会话 ID、权限、任务状态；阶段产物（检索结果/工具返回/草稿答案）挂在具体节点下；③ 收益：减少上下文污染、方便断点恢复、便于定位是哪个角色出的问题；④ 拆分粒度：按"可独立验收的产物"拆，不按"功能点"拆，否则两个 Agent 写同一份结果。

**c 可能追问1**：为什么不用一个 Agent 全干？

**d 追问参考答案1**：上下文压力（所有信息塞一个窗口）、单点失败（一个幻觉毁全部）、难以并行（串行慢）。

**e 可能追问2**：怎么判断拆分粒度合适？

**f 追问参考答案2**：每个子任务能独立验收（有明确产出与判据）、上下文自足（不需要拉别人的全部历史）、失败可隔离（一个失败不传染）。

**g 设计概念详解**：拆分依据是**验收边界**而非功能边界：功能点（查库、写码）可能共享验收（一个功能），产物（检索报告、代码模块）天然独立。阶段产物挂节点下、全局信息进共享区，是"作用域最小化"原则。

### 题52｜多 Agent 并发抢资源怎么办？

**a 问题**：多个 Agent 抢同一资源怎么办？

**b 参考答案**：一句话：先用锁保证互斥，再用异步与队列削峰；选型上回到"可拆解性+并发收益"。要点：① 根因：多个 Agent 同时读写同一份任务/文件/数据库行；② 锁方案：Redis 锁（超时、可重入、续期/看门狗）、数据库行锁、乐观锁版本号；③ 锁阻塞的破法：异步化+队列削峰，避免集体等锁死锁；设锁等待超时与降级路径；④ 更优解：从架构上减少共享——按任务/文件分区，让 Agent 尽量操作不相交的资源。

**c 可能追问1**：锁不是第一选择，为什么？

**d 追问参考答案1**：先做资源分区与单写者，锁只是兜底——锁引入超时、重入、看门狗等复杂度，分区让冲突根本不发生。

**e 可能追问2**：Redis 锁有哪些坑？

**f 追问参考答案2**：超时误释放（业务没跑完锁过期，别的 Agent 进来）→看门狗续期；不可重入→可重入令牌；释放别人的锁→value 存唯一标识，释放前校验。

**g 设计概念详解**：并发控制三级火箭：**架构消除共享**（分区）> **串行化写**（单写者）> **互斥兜底**（锁）。级别越低，复杂度和故障率越高。

### 题53｜Planner / Worker / Reviewer 三角色怎么分工？★高频

**a 问题**：Planner、Worker、Reviewer 怎么分工？

**b 参考答案**：一句话：Planner 只规划、Worker 只执行分到的子任务、Reviewer 只验收；三者的边界靠结构化交接和退回上限约束。要点：① Planner：拆解任务、制定计划、分配子任务——只做规划不执行；计划要可分解、可验收；② Worker：按计划执行并返回结构化结果；防越权——只能执行分到的子任务，不能擅自扩大范围（最小权限+输出 Schema 约束）；③ Reviewer：验收 Worker 结果，质量问题退回并带明确修改意见，或上报 Planner 调整计划；④ 任务传递：传"任务+上下文+当前状态"，不传完整对话历史；⑤ 调度器要点：任务队列+状态机+超时重试+全局日志（task_id 贯穿）；Reviewer 退回次数设上限，防无限循环。

**c 可能追问1**：没有调度器会怎样？

**d 追问参考答案1**：角色不清→重复劳动；没人验收→坏结果一路传递；冲突无人仲裁→死锁卡死。

**e 可能追问2**：Reviewer 太严导致反复退回怎么办？

**f 追问参考答案2**：退回上限+逐轮收紧的验收标准+超限升级人工——先松后严，给 Worker 收敛机会，也防止 Reviewer 用完美标准卡死流程。

**g 设计概念详解**：三角色对应软件工程的**分权制衡**：立法（Planner 定计划）、行政（Worker 执行）、司法（Reviewer 验收）。退回上限是流程收敛机制——没有上限的退回循环等价于死循环。

### 题54｜Agent Swarm 怎么理解？

**a 问题**：Agent Swarm 是什么？多 Agent 协作难点在哪？

**b 参考答案**：一句话：Swarm 可泛指多个 Agent 的动态协作，也可能指具体框架中的交接/路由模式；要先说明所指语境，重点讨论分工、交接、冲突、成本和验收。要点：① Swarm 的形态：规划、检索、执行、评审等角色协同；核心不是 Agent 数量，而是协作机制；② 工程底座（剪映三面考点）：编排层（调度/仲裁）、模型网关（选型路由）、工具服务（统一注册与调用）、记忆存储、任务队列、观测系统（链路追踪/成本计量）；③ 冲突收敛：仲裁者+证据权重为主，投票作辅助（同源模型投票易集体盲从）；④ 成本控制：任务拆分粒度、并行度、每步 Token 预算；并行不是越多越快，受下游与调度限制。

**c 可能追问1**：SWE-bench 类任务多 Agent 的收益来自哪？

**d 追问参考答案1**：并行探索+交叉验证，不是"人多力量大"——多个方案同时试错、互相挑错，收敛速度快于单 Agent 串行。

**e 可能追问2**：Swarm 和 Orchestrator-Worker 的区别？

**f 追问参考答案2**：Swarm 强调动态交接/路由（Agent 间按能力流转控制权），Orchestrator-Worker 是固定中心调度；Swarm 灵活但可观测性差，中心化稳定但扩展性受限。

**g 设计概念详解**：Swarm 的工程本质是**控制权流转协议**：任务在 Agent 之间按能力传递（handoff），每个 Agent 是一个能力节点。难点：交接丢上下文（需要结构化 handoff）、责任漂移（谁最后负责）、成本叠加（每次交接都是一次 LLM 调用）。
