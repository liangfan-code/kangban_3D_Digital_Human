# 敏感事件工单闭环 Spec

## Why

老人对话命中敏感词表后，目前只把事件丢进进程内存队列（`app/services/hitl.py`），没有持久化、没有分派、没有处理闭环：护工/医生看不到，家属不知情，进程重启事件即丢失。老人说"胸口闷"时，系统只能播一句"我帮您叫医生"，实际上没有任何人收到通知。

## What Changes

- 敏感词命中后自动创建**持久化工单**，按角色生成处理项（医生、护理各一条）。
- 新增员工端 WebSocket 通道，工单创建/变更实时推送，员工端自动弹窗并显示未处理数量角标。
- 工单在处理项维度呈现**未读 / 已读 / 已处理**三态；医生、护理分别填写处理方案并各自标记完成。
- 管理员在**医生与护理都提交方案后**可终审关闭工单。
- 家属可只读查看绑定老人工单的状态与处理方案全文。
- 建单时快照**触发前最近 5 轮对话 + 触发句 + 首条安全回复**，供医护人员判断；不存音频、不存整段会话。
- 医生/护理/管理员/家属四类界面均提供历史工单列表，支持**按时间排序**与**关键词搜索**。
- 现有 `GET /admin/hitl/pending` 保留为兜底，但敏感事件的主载体切换为工单。
- 不新增"护工"角色：复用 `AccountRole.NURSE` 同时承担护士/护工职责（见"表述澄清"第 3 条）。

## Impact

- 受影响能力：敏感事件告警、HITL 人工兜底、员工端提醒、家属知情
- 受影响代码：
  - `app/services/voice.py`（`_enqueue_sensitive` 改为建单入口）
  - `app/services/conversation_store.py`（读取触发前最近 5 轮消息用于快照）
  - `app/services/hitl.py`（保留兜底队列）
  - `app/models/workorder.py`、新增处理项与事件表、`alembic/versions/`
  - `app/api/routes/`（新增 staff / family 工单路由）
  - `app/static/{doctor,nurse,admin,family}.html`（工单面板）
  - 新增员工端 WS 通道
- 数据库：新增迁移（不改历史迁移），`workorders` 表扩展字段
- 无新增外部依赖（WS 复用现有 FastAPI WebSocket）

## 表述澄清与遗漏补充

你原话中有 10 处需要明确，以下为默认决策，实现前可再调整：

1. **"护工"与"护士"混用**：系统 `AccountRole` 只有 `nurse`，没有 `worker`/`caregiver`。默认把护理员、护工、护士统一映射为 `nurse`。若必须区分，需新增角色与迁移，成本显著上升。
2. **同一角色多人**：一个老人可能绑定多名医生/护理。默认按**角色维度**建一条处理项，首个操作者认领并记录 `account_id`，其他人只能查看不可重复提交。
3. **"方案落实后可标记已处理"**：默认把"本人提交方案"视为该角色处理完成（`handled`），"落实"不额外校验；工单最终关闭由管理员终审。
4. **三态与现有五态的关系**：`workorders.status` 保留 `open/acknowledged/in_progress/resolved/cancelled`，展示层映射为未读/已读/已处理；处理项使用独立的 `unread/read/handled` 三态，不新增工单枚举。
5. **未处理数量口径**：默认统计"该角色处理项未 `handled` 的工单数"，而不是"未读数量"；角标显示未处理，列表内用未读小圆点区分。
6. **老人身份未识别**：`workorders.elder_id` 是 NOT NULL。默认从设备绑定的房间/老人反推；仍无法确定时**不建工单**，回退到现有 HITL 队列并在日志中记录 `workorder_skipped_no_elder`。
7. **重复触发**：默认同一老人 + 同一敏感类别 + 存在未关闭工单时，不新建工单，累加 `occurrence_count` 并重新推送提醒（避免老人反复说胸口疼刷屏）。
8. **超时升级**：本期不做自动升级/外呼，只做推送与角标；超时策略列为后续项。
9. **家属实时性**：家属端不建 WS 连接，按需拉取（刷新/轮询），避免家属端长连接鉴权复杂度。
10. **隐私边界**：工单保存敏感类别、时间、设备、老人 ID、触发原句，以及**触发前最近 5 轮对话与首条安全回复的快照**（供医护人员判断）；不存整段会话、不存音频；日志只记类别与工单 ID。对话快照默认仅医生、护理、管理员可见，家属看到的是状态与方案全文，不含对话原文（如需开放给家属，仅需放开一处可见范围开关）。
11. **搜索与排序范围**：关键词匹配工单标题、敏感类别、处理方案文本、触发原句；排序支持按创建时间正/倒序与按优先级。历史工单（含已关闭）在四类界面均保留可查，不做物理删除。

## ADDED Requirements

### Requirement: 敏感事件自动建单

系统 SHALL 在对话命中敏感词表且能确定老人身份时，创建一张工单并为 `doctor`、`nurse` 各生成一条处理项。

#### Scenario: 命中急症并建单
- **WHEN** 老人说"我胸口疼，喘不上气"且设备已绑定老人
- **THEN** 创建 `type=sensitive`、`priority=urgent`、`status=open` 的工单
- **AND** 生成 doctor、nurse 两条 `unread` 处理项
- **AND** 向该老人的医生与护理账号推送 `ticket.created`
- **AND** 老人端仍收到安全话术回复

#### Scenario: 老人身份未识别
- **WHEN** 敏感命中但无法确定 `elder_id`
- **THEN** 不创建工单，写入现有 HITL 队列作为兜底
- **AND** 结构化日志记录 `workorder_skipped_no_elder`（不含原文）

#### Scenario: 短时间重复触发
- **WHEN** 同一老人、同一敏感类别已有未关闭工单
- **THEN** 不新建工单，`occurrence_count + 1`
- **AND** 重新推送提醒事件

### Requirement: 敏感事件上下文快照

系统 SHALL 在建单时保存触发前最近 5 轮对话、触发句与首条安全回复，作为医护判断依据。

#### Scenario: 建单携带上下文
- **WHEN** 敏感事件创建工单
- **THEN** 工单保存按时间排序的最近 5 轮对话（用户与助手消息）、触发句、首条安全回复
- **AND** 不保存音频、不保存更多历史消息

#### Scenario: 上下文不足
- **WHEN** 会话历史不足 5 轮
- **THEN** 保存已有全部消息，不报错、不补造内容

#### Scenario: 家属访问
- **WHEN** 家属查看工单详情
- **THEN** 不返回对话快照，仅返回状态与方案全文

### Requirement: 工单检索、排序与历史

系统 SHALL 在医生、护理、管理员、家属四类工单界面提供历史列表、时间排序与关键词搜索。

#### Scenario: 关键词搜索
- **WHEN** 用户在工单列表输入"胸口"
- **THEN** 返回标题、敏感类别、触发原句或处理方案命中该词的工单，且仍受角色可见范围限制

#### Scenario: 按时间排序
- **WHEN** 用户切换排序
- **THEN** 支持按创建时间正序/倒序，默认倒序，分页返回

#### Scenario: 查看历史
- **WHEN** 工单已 resolved
- **THEN** 仍保留在列表中可查可搜，不做物理删除

### Requirement: 三态处理项与方案提交

系统 SHALL 为每条处理项记录未读/已读/已处理状态，并允许对应角色提交处理方案。

#### Scenario: 首次打开工单
- **WHEN** 医生打开工单详情
- **THEN** 该医生处理项由 `unread` 变为 `read`，记录 `read_at` 与操作人
- **AND** 工单状态由 `open` 变为 `acknowledged`，推送 `ticket.updated`
- **AND** 未读状态对护理角色独立，不因医生已读而改变

#### Scenario: 提交处理方案
- **WHEN** 医生填写方案并点击"完成处理"
- **THEN** 处理项变为 `handled`，保存方案全文、操作人、时间
- **AND** 工单状态变为 `in_progress`
- **AND** 推送 `ticket.updated` 给管理员、护理、家属可见范围

#### Scenario: 重复提交
- **WHEN** 处理项已是 `handled` 后再次提交
- **THEN** 返回 409，提示已处理，不覆盖原方案

### Requirement: 管理员终审关闭

系统 SHALL 仅在 doctor 与 nurse 两条处理项都为 `handled` 时允许管理员关闭工单。

#### Scenario: 双方完成
- **WHEN** 医生与护理都已提交方案，管理员点击"标记已处理"
- **THEN** 工单 `status=resolved`，记录 `resolved_at` 与关闭人
- **AND** 推送 `ticket.resolved`，未处理计数减一

#### Scenario: 尚有角色未完成
- **WHEN** 仅一方提交方案时管理员尝试关闭
- **THEN** 返回 409，响应体列出未完成的角色，前端关闭按钮置灰并提示还差谁

### Requirement: 员工端实时推送与未处理角标

系统 SHALL 提供员工端 WebSocket 通道，推送工单事件与未处理数量。

#### Scenario: 新建工单实时弹出
- **WHEN** 医生或护理账号的页面已连接 `/api/v1/staff/ws`
- **THEN** 收到 `ticket.created`，页面自动弹出工单摘要
- **AND** 顶部角标显示当前角色未处理工单数

#### Scenario: 断线与鉴权失败
- **WHEN** 首帧 `auth` 无效或连接断开
- **THEN** 断开连接，页面回退为轮询拉取未处理数量，不静默失败

### Requirement: 家属只读知情

系统 SHALL 允许家属查看绑定老人的工单状态与处理方案全文。

#### Scenario: 家属查看
- **WHEN** 家属账号请求 `GET /api/v1/family/elders/{elder_id}/workorders`
- **THEN** 仅返回该家属有效绑定的老人工单，含三态与方案全文
- **AND** 家属无任何写操作权限

#### Scenario: 越权访问
- **WHEN** 家属请求未绑定老人的工单
- **THEN** 返回 404（不暴露存在性）

### Requirement: 权限矩阵

系统 SHALL 按角色限制工单可见范围与操作。

| 角色 | 查看 | 看对话快照 | 已读 | 提交方案 | 终审关闭 |
|---|---|---|---|---|---|
| doctor | 绑定老人 | 是 | 是 | 是 | 否 |
| nurse | 所负责楼栋/老人 | 是 | 是 | 是 | 否 |
| admin | 全部 | 是 | 否 | 否 | 是 |
| family | 绑定老人 | 否 | 否 | 否 | 否 |

## MODIFIED Requirements

### Requirement: HITL 内存队列

原敏感事件直接进内存队列的行为改为：能建单时以工单为主载体，内存队列仅作为建单失败的兜底与旧接口兼容层；`GET /admin/hitl/pending` 契约保持不变。

## REMOVED Requirements

无。
